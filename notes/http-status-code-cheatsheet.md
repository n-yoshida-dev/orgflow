# HTTPステータスコード チートシート（OrgFlow向け・初学者版）

## 1. まず最短で覚える結論

- **200**: 成功して結果を返す
- **201**: 新規作成に成功した
- **204**: 成功したが返す本文はない
- **400**: リクエストの形式自体がおかしい
- **401**: 未認証。まずログインが必要
- **403**: 認可不足。ログイン済みだが許可されていない
- **404**: 対象が見つからない、または見せない
- **409**: 今の状態ではその操作を実行できない
- **422**: 入力値や業務条件が不正
- **500**: 想定外のサーバー内部エラー

---

## 2. 正常系

### 200 OK

一言でいうと、**成功してレスポンス本文も返す**。

よく使う場面:

- 一覧取得
- 詳細取得
- 更新成功後に更新結果を返す
- ログイン成功後にユーザー情報やトークンを返す

OrgFlow例:

- `GET /requests` で申請一覧を返す
- `GET /audit-logs` で監査ログ一覧を返す
- `POST /login` 成功後にログイン結果を返す

---

### 201 Created

一言でいうと、**新しいリソースの作成に成功した**。

よく使う場面:

- 新規作成API

OrgFlow例:

- `POST /requests` で下書き申請を新規作成した
- `POST /tenants` でtenantを新規作成した

補足:

- 新しく作られた resource のIDや詳細を返すことが多い

---

### 204 No Content

一言でいうと、**成功したが、返す本文は不要**。

よく使う場面:

- 削除成功
- 状態変更成功だが本文を返さない
- ログアウト成功

OrgFlow例:

- `DELETE /requests/{id}/draft` で下書き削除成功
- `POST /logout` 成功
- `PATCH /current-tenant` 成功だが本文なし

補足:

- 「成功したかどうかだけ分かればよい」操作で使いやすい

---

## 3. 異常系

### 400 Bad Request

一言でいうと、**リクエストの形がおかしい**。

典型例:

- JSONの構文が壊れている
- 数値項目に文字列を送った
- 必須パラメータの形式が不正
- UUIDの形式が壊れている

OrgFlow例:

- `amount` に `"abc"` を送った
- path parameter の requestId が UUID 形式ではない

迷いやすい点:

- **「形式が壊れている」なら 400**
- **「形式は正しいが、中身や業務条件がダメ」なら 422**

---

### 401 Unauthorized

一言でいうと、**未認証**。

典型例:

- ログインしていない
- トークンがない
- トークンが期限切れ
- セッションが切れている

OrgFlow例:

- 未ログインで `GET /requests` を呼んだ
- 期限切れトークンで `POST /requests/{id}/approve` を呼んだ

判断の軸:

- その人が**誰か確認できていない**なら 401

---

### 403 Forbidden

一言でいうと、**認可不足**。

典型例:

- ログインはしている
- しかし、その操作をする権限がない
- tenant は合っているが role が足りない
- 自分が承認者ではない request を承認しようとした

OrgFlow例:

- Viewer が承認APIを叩いた
- 自分に request 作成権限がない internal organization に対して申請しようとした
- tenant 管理権限がないのに tenant 設定変更をしようとした

判断の軸:

- その人が**誰かは分かっている**
- でも **その人には許されていない**
- このときは 403

---

### 404 Not Found

一言でいうと、**対象が見つからない**。

典型例:

- 指定したIDの resource が存在しない
- 存在しても、存在を見せない方針を取る
- 別tenantのデータなので見せない

OrgFlow例:

- 存在しない requestId を指定した
- 別tenantの request にアクセスした
- 削除済みまたは参照不可の approval policy を指定した

判断の軸:

- **対象そのものがない**
- または **「あるかどうかも教えない」方が安全**
- このときは 404

補足:

- セキュリティ上、`403` ではなく `404` に寄せる設計もある
- ただし、プロジェクト内で方針を揃えることが重要

---

### 409 Conflict

一言でいうと、**今の状態では安全に処理できない**。

典型例:

- 状態遷移の前提を満たさない
- すでに他の人が処理済み
- 楽観ロック競合
- 二重送信で現在状態と矛盾する

OrgFlow例:

- `draft` ではない request を「提出」しようとした
- すでに `approved` の request を再度承認しようとした
- 承認中に別ユーザーが先に `reject` していた
- 更新対象が古い version だった

判断の軸:

- **入力値は読める**
- **権限もある**
- でも **現在状態や競合のせいで処理できない**
- このときは 409

---

### 422 Unprocessable Entity

一言でいうと、**形式は正しいが、入力値や業務条件が不正**。

典型例:

- 必須項目はあるが値が不正
- バリデーション違反
- 業務ルール違反
- 送った値の意味が成立しない

OrgFlow例:

- `amount = -100`
- `title` が空文字
- 下書き提出時に `amount = 0`
- 申請先 internal organization が current tenant 内でも申請可能条件を満たしていない
- 承認ルート決定に必要な入力が不足している

判断の軸:

- **JSONや型の形式は正しい**
- でも **中身がダメ**
- このときは 422

---

### 500 Internal Server Error

一言でいうと、**想定外のサーバー内部エラー**。

典型例:

- NullPointerException
- ハンドリング漏れ
- DB接続異常を適切に変換できていない
- コードバグ

OrgFlow例:

- 承認処理中に想定外例外が発生した
- 監査ログ保存中に内部例外が起きた
- エラーハンドラで拾っていない例外がそのまま落ちた

注意:

- **業務エラーを 500 で返さない**
- 本来 409 や 422 で返すべきものを 500 に逃がすと設計が弱い

---

## 4. 迷ったときの判断順

次の順で切ると迷いにくい。

### 1. まず認証できているか

- できていない → **401**

### 2. 次に、その人に権限があるか

- 権限がない → **403**

### 3. 次に、対象が存在するか / 見せてよいか

- 存在しない、または見せない → **404**

### 4. 次に、現在状態でその操作が可能か

- 状態遷移や更新競合で無理 → **409**

### 5. 次に、入力値や業務条件が正しいか

- 形式は正しいが中身が不正 → **422**
- 形式自体が壊れている → **400**

### 6. それ以外の想定外

- **500**

---

## 5. すぐ迷う境界

### 401 と 403

- **401**: ログインしていない
- **403**: ログインはしているが権限がない

例:

- トークンなし → 401
- Viewer が承認API実行 → 403

---

### 404 と 403

- **403**: 存在は前提として、あなたには禁止
- **404**: そもそもない、または「あることも教えない」

例:

- 同じtenant内だが role 不足 → 403
- 別tenantの request へアクセス → 404 に寄せることが多い

---

### 409 と 422

- **409**: 現在状態がダメ
- **422**: 入力値や業務条件がダメ

例:

- `approved` 済み request を再承認 → 409
- `amount = -100` → 422
- `draft` 以外を提出 → 409
- 提出時に必須入力不足 → 422

---

### 400 と 422

- **400**: 形式が壊れている
- **422**: 形式は正しいが意味が不正

例:

- `amount: "abc"` → 400
- `amount: -100` → 422

---

## 6. OrgFlowでの最小マッピング例

### ログインAPI

- 成功 → `200`
- ID/パスワード不一致 → `401`
- JSON形式不正 → `400`
- 想定外例外 → `500`

### request作成API

- 成功 → `201`
- 未ログイン → `401`
- 権限不足 → `403`
- internal organization が見つからない / 別tenant → `404`
- 入力値不正 → `422`
- 想定外例外 → `500`

### request提出API

- 成功 → `200` or `204`
- 未ログイン → `401`
- 権限不足 → `403`
- request が見つからない → `404`
- draft 以外を提出 → `409`
- 提出条件を満たさない → `422`
- 想定外例外 → `500`

### 承認API

- 成功 → `200` or `204`
- 未ログイン → `401`
- 承認権限なし → `403`
- 対象 request が見つからない → `404`
- すでに他者が処理済み → `409`
- 承認コメント等の入力不正 → `422`
- 想定外例外 → `500`

### 一覧取得API

- 成功 → `200`
- 未ログイン → `401`
- 閲覧権限なし → `403`
- 0件 → **404ではなく 200 + 空配列**
- 想定外例外 → `500`

---

## 7. 最後に覚えるべき実務感覚

- **401 は「ログインしてない」**
- **403 は「お前には許可してない」**
- **404 は「それはない。あるかどうかも言わないことがある」**
- **409 は「今その状態では無理」**
- **422 は「送った値や業務条件がおかしい」**
- **500 は「設計で吸収できなかった想定外」**
