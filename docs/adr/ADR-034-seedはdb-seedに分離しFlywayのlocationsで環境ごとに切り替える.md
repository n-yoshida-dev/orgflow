# ADR-034: seed は db/seed に分離し、Flyway の locations で環境ごとに適用を切り替える

- Status: Accepted
- Date: 2026-08-25
- 関連: ADR-019（seed を Flyway で管理する判断。本 ADR はその置き場所と適用範囲を更新する） / ADR-029（seed password の保存形式）

> **決定**: seed の SQL は DDL の migration と同じディレクトリに置かず、`db/seed/` に分離する。Flyway の locations 設定で適用範囲を環境ごとに切り替え、既定は「DDL のみ（seed を流さない）」とする。seed を流すのはローカル開発用 profile とテスト設定だけである。

## 背景

Flyway はアプリ起動のたびに走る（ADR-019）。seed が DDL と同居したままデプロイすると、本番 DB にテストユーザーや確認用組織が作られる。しかも seed の password はハッシュとしてリポジトリに載っているため（ADR-029）、既知のパスワードでログインできるアカウントが本番に存在することになる。

ADR-019 は見直す条件に「環境ごとに migration / seed の適用方針を分ける必要が出た場合」を挙げており、テスト基盤の整備でその条件が満たされた。残る論点は、いつ・どの方式で分けるかだった。

## 理由

- 既定を「seed を流さない」側に倒すことで、本番への seed 混入を運用の注意ではなく設定の構造で塞ぐ。流したい環境だけが明示的に locations へ seed を追加する
- Flyway は適用済み migration をバージョン・説明・チェックサムで識別し、ファイルの置き場所を記録しない。そのためファイルを移動するだけで済み、番号の振り直しも適用済み DB への影響もない（移行コストが実質ゼロ）
- デプロイ直前は最も対処したくないタイミングであり、seed が増えるほど移行は重くなる。コストがゼロと分かった時点で先に実施する方が安全
- seed も Flyway 管理のままなので、適用順序は引き続きバージョン番号に任せられる

## 検討した他の案

- **案A: デプロイ準備の段階まで現状維持し、ADR に期限付きで残す** — いま困っていないので対処を遅らせられる。しかし移行コストが実質ゼロと判明した以上、本番事故に直結する作業をデプロイ直前の切迫した時期に残す理由がない
- **案B: seed を Flyway の管理から外し、テストの初期化スクリプト等で投入する** — DDL と seed の分離としては最も明確になる。しかしローカル環境構築の手順が一段増え、seed 同士の適用順序を Flyway に任せられなくなる

## 受け入れる制約

- ローカル起動には profile の指定が必須になる。指定を忘れると、適用済みの seed が locations に見つからず Flyway の整合性チェックで起動が失敗する（黙って seed 抜きで動くのではなく、起動時点で気づける）
- どの環境で何が流れるかは、環境ごとの設定ファイルを読まないと分からない

## 見直す条件

- 開発用 seed とテスト用 seed を別々に持ちたくなった場合（locations をさらに分割する）
- デプロイパイプライン上で migration を明示的に適用する方式へ変えた場合（ADR-019 の見直す条件と同じ）
