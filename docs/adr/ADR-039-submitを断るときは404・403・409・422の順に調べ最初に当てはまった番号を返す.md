# ADR-039: submit を断るときは 404・403・409・422 の順に調べ、最初に当てはまった番号を返す

- Status: Accepted
- Date: 2026-10-11
- 関連: ADR-031（ステータスは次の行動で選ぶ。調べる順番も同じ考え方で決める） / ADR-015（tenant 境界） / ADR-004（`in_progress` に移るときは 0 円を認めない） / ADR-037（状態の規則の置き場所）

> **決定**: API は申請の提出（submit）を受け取ったら、断る理由を次の順番で調べ、最初に当てはまった番号を返す。(1) 申請が自分の tenant に無ければ 404 (2) 送ってきた人が申請者本人でなければ 403 (3) 申請の状態が `draft` でなければ 409 (4) 金額が 0 円なら 422。あわせて、submit できるのは申請者本人だけと決める（(2) の 403 の条件）。

例：1 回の submit に、断る理由が 2 つ同時にあるとき

- A 社の利用者が、B 社の申請（金額 0 円）の ID で submit した → (1) が先に当てはまるので 404。金額の 422 は返さない
- 申請者本人が、自分の取り下げ済み（`cancelled`）で金額 0 円の申請を submit した → (3) が先に当てはまるので 409。金額の 422 は返さない

## 背景

submit では、1 回の送信に、断る理由が 2 つ以上同時にあることがある（上の例）。そのとき API がどの番号を返すかを決めておかないと、実装の書き方しだいで返る番号が変わってしまう。

ADR-031 で、調べる順番は「直しても通らない理由のほうを先に返す」考え方で決めると定めた。ただし ADR-031 が具体的な順番を書いたのは申請の作成についてだけで、submit の順番は決まっていなかった。また、403 を返す条件である「誰なら submit できるか」も決まっていなかった。

## 理由

- 順番の原則は「直しても通らない理由のほうを先に返す」。例：取り下げ済みで 0 円の申請に 422 を返すと、利用者は金額を直して送り直す。しかし状態が `cancelled` のままなので、直しても submit は通らない。先に 409 を返せば、利用者は金額を直すむだな作業をしなくて済む
- tenant の確認（404）を一番先に置く。A 社の利用者が B 社の申請 ID を送ったときに 403 を返すと、A 社の利用者は「その ID の申請は B 社に実在する」と知ることができてしまう。404 なら、ID が実在するかどうかを A 社の利用者に知らせずに済む（ADR-015・031）
- 本人かどうか（403）を状態（409）より先に置く。本人でない人は、申請の状態が何であっても submit できない。また、先に 403 を返せば、本人でない人に他人の申請の状態を知らせずに済む
- 状態（409）を金額（422）より先に置く。理由は 1 つ目の例のとおり
- submit を申請者本人に限ると、申請の「申請者」欄の人と、実際に提出した人が常に同じになる

## 検討した他の案

- **案A: 本人かどうか（403）を一番先に調べる** — A 社の利用者が B 社の申請 ID を送ったときに 403 が返り、その ID の申請が実在すると分かってしまう
- **案B: 金額（422）を状態（409）より先に調べる** — 取り下げ済みや提出済みの申請に「金額を直して送り直して」と伝えることになるが、直しても通らない
- **案C: 同じ組織で申請の権限（requester role）を持つ人なら、本人でなくても submit できる（代理の提出）** — 申請者欄の人と、提出した人が一致しなくなる。代理の提出は Phase 1 の範囲に入れていない

## 受け入れる制約

- 順番を変えると、同じ送信に返る番号が変わる。画面は返ってきた番号を見て表示を変えるので、順番の変更は OpenAPI（API の約束）の変更と同じ扱いにする（ADR-031）
- API は submit のときに、申請者がまだ申請の権限（requester role）を持っているかを確かめない。Phase 1 には権限を外す操作が無く、作成時に確かめた権限が submit のときにも残っているため

## 見直す条件

- 本人以外による代理の提出を認める要件が出たとき
- 権限を外す操作が入り、申請を作ったあとに権限を外された人の submit を断る必要が出たとき
