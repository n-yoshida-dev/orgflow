# ADR-035: 状態列は PostgreSQL の enum 型ではなく text と CHECK 制約で表現する

- Status: Accepted
- Date: 2026-08-25
- 関連: ADR-004（状態を明示的な状態モデルで表現する。本 ADR はその DB 上の表現方法）

> **決定**: `requests.status` と `audit_logs.operation_type` は PostgreSQL の enum 型をやめ、text 列と CHECK 制約で表現する。許容値の変更は CHECK 制約の付け替えで行う。

## 背景

状態列を PostgreSQL の enum 型（`CREATE TYPE ... AS ENUM`）で定義していたところ、JPA からの INSERT が「列の型は enum 型だが、渡された値の型は varchar」として弾かれた。JDBC ドライバは Java の String をパラメータとして送るとき「この値は varchar である」と PostgreSQL に申告し、PostgreSQL は varchar から独自 enum 型への暗黙の変換を行わないためである（psql で文字列リテラルを直接打つと通るのは、リテラルが型未定として送られ、列の型に合わせて解釈されるから）。

一方、同じテーブルの `request_type` は最初から text と CHECK 制約で定義されており、状態列だけが enum 型という不揃いがあった。型を合わせる場所は3つ考えられる。DB 側（列を text にする）、Java 側（Java の enum と DB の enum 型を対応付ける指定を足す）、JDBC ドライバ側（型の申告をやめて DB に解釈させる）である。

## 理由

- スキーマが一貫する。`request_type` と同じ「text＋CHECK」に揃い、列ごとに方式を使い分けなくてよい
- Java 側の変更が不要で、JPA 固有のマッピング設定を持ち込まない。エンティティは単なる String のまま
- 許容値の追加・削除が CHECK 制約の付け替えで済む。PostgreSQL の enum 型は値の削除ができず、追加にも制約が多いため、状態が増減する開発段階では扱いづらい
- 許容値の一覧が DDL の CHECK 制約に明示され、スキーマを読むだけで分かる

## 検討した他の案

- **案B: Java 側のフィールドを enum にし、DB の enum 型へ対応付ける指定を持たせる** — DB の型として不正値を弾けるため、型の厳密さは最も高い。しかし対象の全列に対応付けの指定が要り、text のままの `request_type` と方式が割れたまま残る
- **案C: JDBC の接続パラメータで、String を varchar と申告せず型未定で送り、DB に解釈させる** — コード変更もスキーマ変更も不要で、対処としては最小。しかし接続文字列の末尾の一つのフラグが、全テーブルの全 String 列の扱いを変える。後からコードとスキーマを読んでもフラグの存在に気づけず、見えない一行に全体が依存する。標準から外れた設定を増やさない方針に反する

## 受け入れる制約

- DB 上の型は単なる text であり、CHECK 制約を外せば何でも入る。型そのもので守る enum 型より厳密さは劣る
- 許容値が CHECK 制約と Java 側の定数の二重管理になり、片方だけ更新すると食い違う

## 見直す条件

- 状態の種類が大きく増え、CHECK 制約の付け替えによる管理が煩雑になった場合
- JPA 側で enum マッピングを全面的に採用する方針へ変えた場合（そのとき `request_type` も含めて方式を統一する）
