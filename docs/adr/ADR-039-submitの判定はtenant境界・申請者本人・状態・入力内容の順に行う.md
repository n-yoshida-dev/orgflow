# ADR-039: submit の判定は tenant 境界・申請者本人・状態・入力内容の順に行う

- Status: Accepted
- Date: 2026-10-11
- 関連: ADR-031（次の行動で選ぶ。判定の順序は仕様の一部） / ADR-015（tenant 境界） / ADR-004（submit 時の入力検証） / ADR-037（状態の規則の置き場所）

> **決定**: submit は次の順に判定し、最初に該当したものを返す。(1) 自分の tenant の申請でなければ 404 (2) 申請者本人でなければ 403 (3) 状態が `draft` でなければ 409 (4) 金額が 0 円なら 422。submit できるのは申請者本人だけとする。

## 背景

submit では、1 つの要求が複数の条件に同時に該当しうる。たとえば「他 tenant の申請で、しかも金額が 0 円」や「取り下げ済みで、しかも金額が 0 円」である。

ADR-031 で、複数に該当する場合は「返したステータスが導く行動で、実際に解決する順」に判定すると決めたが、具体的な順序は申請作成についてしか定めていなかった。あわせて、403 の条件となる「誰が submit できるか」も決まっていなかった。

## 理由

- 直しても通らない理由を先に返す。後の条件を直しても前の条件で必ず失敗するなら、後の条件を伝えても解決しない
- tenant 境界を最初に判定する。他の番号を先に返すと、他 tenant に存在する申請の識別子かどうかを外から確かめられてしまう（ADR-015・031）
- 申請者本人の判定を状態より先に置く。本人でなければ、状態がどうであっても submit できない。本人でない者に、他人の申請の状態を伝えずに済む
- 状態を金額より先に置く。取り下げ済みの申請に 422 を返すと、金額を直して送り直しても submit は通らない
- submit を申請者本人に限ることで、誰が申請したかが申請の記録と一致する

## 検討した他の案

- **案A: 申請者本人の判定を最初に置く** — 他 tenant の申請に 403 を返すことになり、識別子の存在が分かってしまう
- **案B: 金額（422）を状態（409）より先に判定する** — 取り下げ済みや申請済みの申請に「金額を直して再送」を促すが、直しても通らない
- **案C: 同じ組織で requester role を持つ者なら誰でも submit できる（代理申請）** — 申請者と submit した者が一致しなくなる。Phase 1 の範囲を超える

## 受け入れる制約

- 判定の順序が契約の一部になるため、順序を変える変更は契約の変更として扱う（ADR-031）
- submit の時点で、申請者が requester role を持ち続けているかは確かめない。Phase 1 には role を外す操作がない

## 見直す条件

- 代理申請を認める要件が出た場合
- role を外す操作が入り、作成後に requester role を失った申請者の submit を拒む必要が出た場合
