# ADR-007: request を「申請版」の単位として扱う

- Status: Accepted
- Date: 2026-03-24
- 関連: ADR-004（状態遷移） / ADR-005（request の参照方式）

> **決定**: request は「申請版」を表す単位として扱う。同一申請の系列を `request_series_id`、版を `version_no` で識別し、その組に一意制約を置く。参照用の主キーは `request.id` を別に持つ。

## 背景

request は差し戻し後に内容を修正して再申請される。このとき、差し戻し前の内容と再申請後の内容の両方を残し、後から履歴として説明できる必要がある。

既存 request を上書きすると、どの時点で何を申請していたのかが追えなくなる。監査ログ、状態遷移、差し戻し後の再申請を一貫して説明できる構造が必要だった。

## 理由

- 差し戻し前後の申請内容が両方残るため、何を直して再申請したのかを示せる
- どの版がどの状態で終わったか（`returned` で終わった版、`approved` になった版）を版ごとに説明できる
- 監査ログと組み合わせたときに「いつ・どの版に対して・何が起きたか」を追える
- request を「ある時点の申請内容」として扱う整理（ADR-004）と一致する

## 検討した他の案

- **案A: 既存 request を更新し続ける** — 過去の申請内容が失われ、差し戻し前後の差分を示せない
- **案B: request 本体とは別に version テーブルを持つ** — request 本体と版の責務分担が増え、どちらに何を書くかの判断が毎回必要になる。まず request 自体を申請版として扱うほうが構造が単純

## 受け入れる制約

- 1つの申請を追うには系列単位での取得が必要になる
- レコード数が増える
- 「最新版だけを見る処理」と「系列全体を見る処理」を分けて実装する必要がある

## 見直す条件

- 版ごとの差分表示や比較機能が必要になった場合
- 版ごとの共通情報と差分情報を分離したほうが明らかに有利になった場合
- 申請版として持つ構造ではクエリや実装の負荷が高すぎると判明した場合
