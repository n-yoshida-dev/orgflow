# ADR-030: 監査ログは業務処理と同一トランザクションで書く

- Status: Accepted
- Date: 2026-08-21
- 関連: ADR-002（監査ログを独立した概念として扱う） / ADR-011（audit_log の保持方法）

> **決定**: 業務処理（request の作成・状態変更など）と、その操作の監査ログの書き込みは、同一のデータベーストランザクションで行う。どちらか一方だけが DB に残る状態を作らない。

## 背景

監査ログは「誰が・いつ・何をしたか」を後から追跡するための証跡である（ADR-002）。

業務処理と監査ログの書き込みを別々に行うと、障害が起きたタイミングによって「申請は作られたのに監査ログがない」か「監査ログはあるのに申請が存在しない」のどちらかが起きる。前者は証跡の欠落、後者は実体のない証跡であり、どちらも監査ログの役割を損なう。

申請作成を実装するにあたり、この2つの書き込みをどう結びつけるかを決める必要があった。

## 理由

- 業務処理と監査ログが「一緒に成功するか、一緒に失敗するか」のどちらかになり、証跡の欠落も実体のない証跡も構造的に起きない
- 監査ログが欠けても後から補えない。操作時点の表示名や所属のスナップショット（ADR-011）は、時間が経つと再現できないため、「業務処理だけ先に通してログは後で書く」は成立しない
- キュー・再送・突き合わせバッチのような追加の仕組みを持たずに整合性を保てる。現在の規模では最も単純な方法である
- 整合性を可用性より優先する判断である。監査ログを書けない状態で業務処理だけ進めるより、処理ごと失敗させて利用者に再試行させる方が、監査要件に対して安全である

## 検討した他の案

- **案A: 監査ログを別トランザクションで書く（業務処理のコミット後に独立して書き込む）** — 業務処理は監査ログの失敗に影響されなくなるが、監査ログ側が失敗したときに証跡の欠落が残る。欠落を検知・補填する仕組みが別途必要になり、現時点で持つには重い
- **案B: 非同期に書く（イベントやキューを経由して後から書き込む）** — 業務処理の応答時間から監査ログを切り離せ、外部のログ基盤とも相性がよい。しかしイベントの取りこぼし・順序・重複への対処が必要で、「必ず残る」を保証するには案Aと同じ補填の仕組みが要る。現時点の規模では過剰
- **案C: DB トリガーで書く** — アプリ側の実装漏れがあっても必ず記録される利点はあるが、「誰が操作したか」は認証情報（JWT）にしかなく、DB の行には渡らない。トリガーは書き込まれた行しか見えないため、操作主体とそのスナップショット（ADR-011）を記録できない。記録のロジックも DB とアプリに分散する

## 受け入れる制約

- 監査ログの書き込みが失敗すると、業務処理も失敗する（ロールバックされる）。監査ログのためにサービスが止まる方向に倒している
- 監査ログは業務データと同じ DB に書く前提になる。外部のログ基盤へ直接送る構成は、同一トランザクションに含められないため取れない
- 1つの業務処理で書く監査ログが増えるほど、トランザクションが長くなる

## 見直す条件

- 監査ログを外部の基盤（ログ集約サービス等）へ送る必要が出た場合
- イベント駆動設計を導入し、監査ログをイベント履歴から導出する構成に変える場合（ADR-002 の見直す条件と同じ）
- 監査ログの書き込みが業務処理の応答時間に影響するようになった場合
