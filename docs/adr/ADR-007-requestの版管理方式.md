# ADR-007: request の版管理方式

- Status: Accepted
- Date: 2026-03-24

## 背景

- request は、差し戻し後に内容を修正して再申請される
- このとき、差し戻し前の内容と再申請後の内容の両方を保持し、後から履歴として説明できる必要がある
- 既存 request を上書きすると、どの時点で何を申請していたのかが追いにくくなる
- 監査ログ、状態遷移、差し戻し後の再申請を一貫して説明できる構造が必要だった

## 採用した案

request は「申請版」を表す単位として扱う。

- 差し戻し後の再申請では既存 request を更新せず、新しい request を作成する
- 同一申請の系列は `request_series_id` で表現する
- 各版は `version_no` で識別する
- `(request_series_id, version_no)` に一意制約を置く
- 参照用主キーとして `request.id` を別に持つ

## 採用理由

- 差し戻し前後の申請内容を失わずに保持できる
- どの版がどの状態で終わったかを明確に説明できる
- 監査ログと組み合わせたときに、「いつ・どの版に対して・何が起きたか」を追いやすい
- request を「ある時点の申請内容」として扱う整理と整合する

## 不採用案

### 案A: 既存 request を更新し続ける

- 過去の申請内容が失われる
- 差し戻し前後の差分を説明しにくい
- 監査ログや履歴説明との整合が悪くなる

### 案B: request 本体とは別に version テーブルを持つ

- Phase 1 では構造が複雑になりすぎる
- request 本体と版の責務分担が初見で分かりにくくなる
- まずは request 自体を申請版として扱う方が説明しやすい

## 受け入れる制約

- 同一申請を取得する際に、系列単位での取得が必要になる
- レコード数は増える
- 「現在の最新版だけを見る処理」と「系列全体を見る処理」を分けて考える必要がある

## 見直す条件

- 版ごとの差分表示や比較機能を強く求めるようになった場合
- 版ごとの共通情報と差分情報を分離した方が明らかに有利になった場合
- request を申請版として持つ構造ではクエリや実装の負荷が高すぎると判明した場合
