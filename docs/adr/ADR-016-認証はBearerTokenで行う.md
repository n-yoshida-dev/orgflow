# ADR-016: 認証は Bearer token（JWT / HS256）で行う

- Status: Accepted
- Date: 2026-04-19
- 関連: ADR-020（Security 構成） / ADR-021（ログイン認証） / ADR-022（JWT の発行と検証） / ADR-023（userId の取得） / ADR-024（tenant 選択状態）

> **決定**: 認証方式として Bearer token（JWT / HS256）を採用する。OpenAPI 上でも `bearerAuth` として契約に明記し、認証必須 API と認証不要 API を区別する。

## 背景

Phase 1 のスコープは、認証済み API を前提とした RBAC・業務フロー・監査ログの実装に置いた。認証基盤そのものの作り込みはスコープ外とする。

一方で、認証方式は API 契約・フロントエンド連携・後続フェーズの実装言語（Go への置き換え）すべてに影響する。後から差し替えるコストが大きいため、実装に入る前に決める必要があった。

## 理由

- サーバー側にセッションストアを持たないため、認証状態の保存先を用意せずに済む
- React、その後の Go 実装のどちらからも扱いやすく、後続フェーズを制約しない
- OpenAPI で `bearerAuth` として表現でき、認証必須 API と認証不要 API の違いが契約上明示できる
- token に claim を載せることで、認証済み主体や選択中 tenant を API 間で引き回せる（ADR-023、ADR-024）

## 検討した他の案

- **案A: セッションベース認証** — Cookie の SameSite / Secure 設定と CSRF 対策が前提になる。Phase 1 のスコープは認可と業務フローであり、そこに入る前の作り込みが増える
- **案B: 外部 IdP（OIDC）前提** — 実務では有力だが、IdP の構築と設定が主作業になり、Phase 1 のスコープから外れる

## 受け入れる制約

- token の失効・更新（refresh token）・クライアント側の保管戦略は Phase 1 では扱わない
- HS256（共通鍵）のため、署名鍵をアプリケーション自身が持つ。鍵の配布・ローテーションが必要な構成には向かない
- ログアウトでサーバー側から token を無効化できない。有効期限切れを待つ前提になる

## 見直す条件

- Phase 2 で React と接続し、token の更新・保管が実装論点になったとき
- 外部 IdP 連携や SSO の要件が入ったとき
- 複数サービスで token を検証する構成になり、公開鍵方式（RS256）が必要になったとき
