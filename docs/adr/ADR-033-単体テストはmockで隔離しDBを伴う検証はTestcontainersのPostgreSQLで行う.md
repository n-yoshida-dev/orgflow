# ADR-033: 単体テストは mock で隔離し、DB を伴う検証は Testcontainers の PostgreSQL で行う

- Status: Accepted
- Date: 2026-08-23
- 関連: ADR-018（ローカル開発DBを Docker Compose の PostgreSQL で起動する） / ADR-019（DBマイグレーションと seed を Flyway で管理する）

> **決定**: テストを2層に分ける。単体テストは Repository を mock に置き換え、Service の判断（検証の順序・例外の種別）だけを検証する。SQL・DB 制約・migration の正しさは、本番と同じ PostgreSQL を Testcontainers でテスト実行時に起動する結合テストで担保する。ローカルでも CI でも同じ仕組みで動かす。

## 背景

申請作成の実装時点でテストは起動確認の1本しかなく、Service の分岐（所属外 422・role 無し 403・正常系）も、migration で作った制約や SQL の正しさも、Postman の手動確認でしか検証されていなかった。

テストを書くにあたり、2つを決める必要があった。(1) 単体テストと結合テストで何を検証し分けるか。(2) 結合テストが使う DB をどう用意するか。テスト設定が開発用 DB を直接向いていたため、DB を伴うテストを書くと開発データを壊し、CI でも動かない状態だった。

## 理由

- 落ちたときに疑う対象を狭められる。単体テストは Repository が mock なので、赤くなれば原因は Service の判断ロジックに限られる。結合テストが赤くなれば SQL・制約・migration のどれかに限られる
- 本番と同じ PostgreSQL で検証するため、`gen_random_uuid()`・`::` キャスト・CHECK 制約など PostgreSQL 固有の要素がそのまま検証できる。別の DB で通っても本番で通る保証にはならない
- ローカルと CI が同じ仕組み（テスト実行時にコンテナを起動）で動くため、「CI でだけ落ちるがローカルで再現できない」が構造的に起きない。CI 側に DB を準備する手順を別途持たずに済む
- コンテナはランダムポートで起動し、テスト終了時に破棄されるため、開発用 DB と衝突せず、テストデータも残らない
- 接続先は Spring Boot がコンテナから自動で注入するため、テスト設定から接続先の記述が消え、「どの DB を向いているか」を人が管理しなくてよい

## 検討した他の案

- **案A: 結合テストだけにして単体テストは書かない** — DB まで通すので検証としては最も実態に近く、mock の準備も要らない。しかし Spring のコンテキスト起動と DB アクセスを伴うため1本ごとの実行が重く、落ちたときに Service の判断か SQL かの切り分けが毎回必要になる
- **案B: GitHub Actions の service container で DB を用意する** — CI ではコンテナ起動が軽い。しかし接続先の指定がワークフロー側にしか無く、ローカルで同じ結合テストを実行できない。仕組みが CI 用とローカル用に割れ、失敗時の切り分け箇所も増える
- **案C: H2 などのインメモリ DB** — 起動が速く Docker も不要。しかし migration が PostgreSQL 固有構文を使っており動かない。互換モードで動かしても本番と別物の DB を検証することになり、結合テストの目的（SQL と制約の正しさ）を満たさない
- **案D: 開発用 DB（Docker Compose）をそのまま使う** — 追加の仕組みが不要。しかしテストが開発データを壊し、開発用 DB が止まっていれば動かず、CI には存在しない

## 受け入れる制約

- テスト実行に Docker が必要になる。Docker の無い環境では結合テストを実行できない
- コンテナ起動の分だけテスト時間が延びる。CI では PostgreSQL イメージの取得も毎回発生する
- 単体テストの mock は Repository の振る舞いを決め打ちするため、Repository の実装と食い違っても単体テストでは検出できない。その食い違いは結合テストで拾う前提になる

## 見直す条件

- CI の実行時間がコンテナ起動のオーバーヘッドで許容できなくなった場合（その場合もローカルは Testcontainers のまま、CI だけ service container に寄せる折衷を先に検討する）
- テストクラスが増え、コンテキストの構成差でコンテナが複数回起動するようになった場合
