# ADR-011: audit_log の操作対象参照方式と操作主体の保持方法

- Status: Accepted
- Date: 2026-03-25

## 背景

- `audit_log` は `request`・`approval`・`user`・`approval_policy` など、複数の種別の概念を横断して操作を記録する必要がある
- 監査ログでは、単に対象を機械的に追えるだけでなく、人が後から読んで「誰が・どの組織で・何に対して・何をしたか」を理解できる必要がある
- 決めないと、参照先レコードの削除や表示名変更のあとに、監査記録の可読性や追跡性が落ちる
- Phase 1 では、監査ログは後付けの補助機能ではなく、業務フローの一部として扱う

## 採用した案

- 操作対象は `target_type` と `target_id` の2カラムで保持する
- `target_id` に対する外部キー制約は置かない
- 一方で、操作主体については `user_id` と `actor_organization_id` を保持する
- さらに、監査画面で人が読めるように、操作時点の表示用スナップショットとして次を保持する
  - `actor_user_display_name`
  - `actor_user_mail_address`
  - `actor_organization_name`

## 採用理由

- 監査ログは操作時点の不変な証跡であり、対象レコードが後から削除されても記録を失ってはいけない
- `target_type` と `target_id` を分けることで、`WHERE target_type = 'request' AND target_id = ?` のように対象別の検索を書きやすい
- 操作主体については、ID だけでは監査画面で読みにくい
- 逆に表示名や組織名だけでは、同名ユーザーや後日の照合に弱い
- そのため、操作主体は「IDによる追跡性」と「表示用スナップショットによる可読性」の両方を持つ

## 補足

- `target_id` に外部キーを置かないのは、監査対象側の削除や変更で監査記録の意味を失わないためである
- `user_id` と `actor_organization_id` は、操作主体を機械的に追跡するために保持する
- `actor_user_display_name`、`actor_user_mail_address`、`actor_organization_name` は、監査画面でそのまま読める証跡にするために保持する
- 表示用スナップショットは、親テーブルの値が後から変わっても自動では更新しない

## 不採用案

### 案A: 各対象テーブルへの外部キー制約を持つ

- 不採用理由
  - 参照先削除時に制約エラーが発生するか、削除を禁止しすぎる
  - 監査ログが「不変な証跡」であるという性質と相性が悪い

### 案B: 対象種別と識別子を1カラムにまとめる（例: `request:uuid`）

- 不採用理由
  - WHERE 句での検索が扱いにくい
  - インデックス設計も不自然になる

### 案C: 操作主体を表示名やメールアドレスだけで持つ

- 不採用理由
  - 同名ユーザーや表示名変更後の追跡に弱い
  - 機械的な照合が難しい

### 案D: 操作主体を ID だけで持つ

- 不採用理由
  - 監査画面で人が読む証跡としては分かりにくい
  - 表示名や organization 名が後から変わると、操作時点の状況を読み取りにくい

## 受け入れる制約

- `target_id` の参照整合性は DB が保証しない
- 操作主体については、ID と表示用スナップショットの両方を保持するため、列数が増える
- 表示用スナップショットは、後から親テーブルの値が変わっても自動では更新しない
- users / organizations の削除戦略によっては、操作主体側の FK の扱いを別途再整理する必要がある

## 見直す条件

- 監査ログの検索要件が複雑化し、対象種別ごとに専用テーブルを持つ方が有利になった場合
- 認証基盤の分離や外部 IdP 連携により、操作主体の保持方法を再整理する必要が生じた場合
- 物理削除戦略の見直しにより、`user_id` / `actor_organization_id` の保持方針を再検討する必要が生じた場合
