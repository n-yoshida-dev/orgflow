# ADR-031: HTTP ステータスは「クライアントが次に何をすべきか」で選ぶ

- Status: Accepted
- Date: 2026-08-22
- 関連: ADR-015（tenant 境界） / ADR-026（申請先に選べる組織の条件） / ADR-017（OpenAPI を契約とする） / ADR-032（エラー応答の文言）

> **決定**: エラー時の HTTP ステータスは、エラーの原因がどこにあるかではなく、「そのステータスを受け取ったクライアントが次に何をすれば解決するか」で選ぶ。複数の条件に同時に該当しうる場合は、返したステータスが導く行動で実際に解決する順に判定する。

## 背景

申請作成では「tenant を選んでいない」「指定した組織に所属していない」「所属はあるが申請 role がない」「組織が存在しない」が別々のエラーとして起きる。これらに 403 / 404 / 422 のどれを返すかは、定義（権限不足・未発見・処理不能）だけでは決まらない。たとえば「所属していない組織」は、権限不足とも入力不正とも読める。

決めないと endpoint ごとに判断がぶれ、同じ状況に別のステータスが返る。クライアントはステータスを見て次の行動を決めるため、ぶれると「何をすれば通るのか」が伝わらない。

## 理由

- クライアントが HTTP ステータスから読み取るのは「自分は次に何をすべきか」である。ステータスをその行動に対応づけておけば、メッセージ本文を解釈しなくても復旧手順が決まる
- 判定の順序も同じ基準で決まる。先に返したステータスの行動で解決しないなら、その順序は誤りである
- 到達しないはずの分岐（前段の判定を通過したのに参照先が存在しない等）は、クライアントの行動では解決しない。4xx で返すと誤った行動を誘導するため、サーバー側の不具合として 500 にする

### ステータスと「次の行動」の対応

| ステータス | 状況 | クライアントの次の行動 |
|---|---|---|
| 401 | 認証情報がない、または不正（ログイン失敗、JWT の欠落・改ざん・claim の形式不正） | ログインし直す |
| 403 | 認証は済んでいるが、操作の条件を本人が満たしていない（tenant 未選択、role がない） | 入力を変えても通らない。tenant を選択する、または管理者に権限付与を依頼する |
| 404 | 対象が存在しない、または操作者の tenant から見えない（所属しない tenant の選択、他 tenant の request） | 指定した識別子を見直す |
| 409 | 対象は見えるが、現在の状態では処理できない（draft でない request の submit 等） | 最新の状態を取り直して判断する |
| 422 | 形式は正しいが、この操作者にとって処理できない値（所属していない組織の指定）、または形式不備 | 入力を直して再送する |
| 500 | 到達しないはずの分岐に入った | できることはない。サーバー側で調査する |

### 判定の順序（申請作成）

「所属していない」（422）を「role がない」（403）より先に判定する。

逆順にすると、所属していない組織を指定した利用者に 403 が返る。403 は「権限さえ付けば通る」と伝えるため、利用者は管理者に role の付与を依頼しに行く。しかし実際は組織の指定が誤っているだけなので、依頼しても解決せず、本来返るべき 422 が出ない。

### tenant 境界の外は 404 にする

他 tenant の資源を指定された場合は、403（権限がない）ではなく 404（存在しない）を返す。403 を返すと「その識別子は存在する」と教えることになり、tenant 境界を越えた存在確認に使われる（ADR-015）。

## 検討した他の案

- **案A: エラーの原因箇所で決める（認可の判定で落ちたら 403、値の検証で落ちたら 422）** — 実装の構造に依存するため、同じ状況でも判定をどこに置くかでステータスが変わる。クライアントには実装の構造は見えない
- **案B: 所属と role の判定を 403 にまとめる** — 判定が1つ減り単純になるが、「組織の指定が誤っている」と「権限がない」を区別できず、利用者が誤った復旧行動を取る
- **案C: 到達しない分岐も 404 / 422 にする** — クライアントに「入力を直せば通る」と誤って伝える。サーバー側の不具合が 4xx に埋もれて監視で検知できない

## 受け入れる制約

- 新しい endpoint を追加するたびに、各エラーを「次の行動」に当てはめて判断する必要がある。機械的には決まらない
- 422 の応答文言は「所属していない」と述べるため、組織の存在自体は隠さない。tenant 内の組織については存在を隠す要件を置いていない
- 判定の順序が仕様の一部になるため、順序を変える変更は契約の変更として扱う

## 見直す条件

- RFC 9457（Problem Details）のような構造化エラー形式を採用し、ステータスに加えてエラー種別を本文で返すようになった場合
- tenant 内の組織や request についても存在を隠す要件が出た場合
- クライアントが機械的に復旧行動を選ぶ必要が出て、ステータスだけでは粒度が足りなくなった場合
