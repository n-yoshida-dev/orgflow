# ADR-009: applied_approval_route を親子構造で保持する

- Status: Accepted
- Date: 2026-03-24

> **決定**: 承認ルートの適用結果を `applied_approval_routes` / `_steps` / `_step_approvers` の親子3層で保持し、1つの承認段に複数承認者を持てる構造とする。

## 背景

- 承認ルートは、ルート全体、各承認段、各段の承認者という複数の粒度を持つ
- 1つの承認段に複数承認者が存在する可能性がある
- request ごとの適用結果を保存するにあたり、どの粒度で分けて保持するかを決める必要があった
- 承認段と承認者を同じ粒度で持つと、責務が混ざって分かりにくくなる

## 採用した案

承認ルートの適用結果は、次の3層で保持する。

- `applied_approval_routes`: ルート全体
- `applied_approval_route_steps`: 承認段
- `applied_approval_route_step_approvers`: 承認者

1つの承認段には複数承認者を持てる構造とする。

## 採用理由

- ルート全体、承認段、承認者の粒度を分離できる
- 1段に複数承認者がいる業務ルールを自然に表現できる
- 正規化された構造として保持できる
- 後から「どの段に誰がいたか」「どの段が完了したか」を追いやすい
- ADR-010 の「同一段で誰か1人が承認すれば完了」というルールとも整合する

## 不採用案

### 案A: 1テーブルでまとめて保持する

- 承認段と承認者の粒度が混在する
- 同じ段に複数承認者がいる場合の表現が不自然になる
- 段単位の状態や順序を扱いにくい

### 案B: 1段1承認者に制限する

- 実務上ありうる「同一段に複数承認者」を表現できない
- ルート定義の自由度が不必要に下がる

### 案C: JSON で1カラムに保持する

- SQL での検索、検証、テスト、監査が扱いにくい
- 段単位・承認者単位の追跡がしにくい

## 受け入れる制約

- テーブル数が増える
- JOIN が増える
- 初見では `approval_route` / `applied_approval_route` / `step` / `approver` の違いを理解するコストがある

## 見直す条件

- 承認ルートの複雑度が上がり、3層構造ではクエリや実装が現実的でなくなった場合
- 全員承認や条件分岐など、段ごとの表現をさらに拡張する必要が出た場合
- より適切な保存構造へ変更した方が、説明性と実装コストの両面で有利になった場合
