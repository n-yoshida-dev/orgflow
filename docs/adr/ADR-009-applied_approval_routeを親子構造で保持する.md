# ADR-009: applied_approval_route を親子3層で保持する

- Status: Accepted
- Date: 2026-03-24
- 関連: ADR-008（適用結果を保存する理由） / ADR-010（同一段の完了条件） / ADR-006（Superseded、同一結論）

> **決定**: 承認ルートの適用結果を `applied_approval_routes`（ルート全体）/ `applied_approval_route_steps`（承認段）/ `applied_approval_route_step_approvers`（承認者）の親子3層で保持し、1つの承認段に複数の承認者を持てる構造とする。

## 背景

承認ルートは、ルート全体・各承認段・各段の承認者という3つの粒度を持つ。さらに、1つの承認段に複数の承認者が存在しうる。

ADR-008 で適用結果を保存すると決めたが、どの粒度で分けて保持するかは決めていなかった。承認段と承認者を同じ粒度で持つと、段の順序や完了状態を承認者ごとに重複して持つことになる。

## 理由

- ルート全体・承認段・承認者の粒度を分離でき、段の順序や完了状態を段のレコードだけで表せる
- 1段に複数の承認者がいる業務ルールを、承認者テーブルの複数行として素直に表現できる
- 正規化された構造なので、「どの段に誰がいたか」「どの段が完了したか」を SQL で追える
- 同一段は誰か1人の承認で完了する（ADR-010）というルールと、段が承認者リストを持つ構造が一致する

## 検討した他の案

- **案A: 1テーブルにまとめて保持する** — 承認段と承認者の粒度が混在し、段の順序や完了状態を承認者の行数だけ重複して持つことになる
- **案B: 1段1承認者に制限する** — 実務でありうる「同一段に複数承認者」を表現できず、ルート定義の自由度が不必要に下がる
- **案C: JSON で1カラムに保持する** — 段単位・承認者単位の検索と検証が SQL で扱いにくく、承認者ごとの完了状態を追跡しづらい

## 受け入れる制約

- テーブル数と JOIN が増える
- `approval_route`（テンプレート）と `applied_approval_route`（適用結果）、`step`、`approver` の違いを理解しないと構造を追えない

## 見直す条件

- 承認ルートの複雑度が上がり、3層構造ではクエリや実装が現実的でなくなった場合
- 全員承認や条件分岐など、段ごとの表現を拡張する必要が出た場合
