# ADR-001: 題材として申請・承認フローを持つ業務アプリを採用する

- Status: Accepted
- Date: 2026-03-19

> **決定**: 題材として、申請・承認フローを持つ業務アプリを採用する。

## 背景

Phase 1 では、REST API 中心の業務アプリとして成立する設計を扱う必要があった。

Todo やタスク管理のような単純な CRUD では、承認フロー、組織ごとのデータ分離、RBAC、監査ログといった論点が題材の中に自然に現れない。無理に足すと、機能と題材が噛み合わない成果物になる。

## 理由

- 申請 → 承認 → 監査という業務フローが題材そのものに含まれるため、状態遷移を後付けせずに扱える
- organization / role / request / approval / audit_log を別々の概念として分離でき、それぞれの責務を説明できる
- 承認者の権限、他組織のデータの見えかたなど、認可の判断が題材から自然に出てくる
- SPA、通知、監査 UI といった拡張の余地がある

## 検討した他の案

- **案A: Todo アプリ** — 状態遷移が「未完了 / 完了」しかなく、権限と監査の論点がほぼ出てこない
- **案B: タスク管理アプリ** — 担当者の割り当てはあるが、承認と監査を組み込むと題材として不自然になる

## 受け入れる制約

- 画面の見た目のインパクトは弱い
- 業務の前提知識が必要なため、初見で理解するコストが高い

## 見直す条件

- UI での訴求を強める必要が出た場合（ダッシュボードや通知機能の追加）。ただし題材自体は変更しない
