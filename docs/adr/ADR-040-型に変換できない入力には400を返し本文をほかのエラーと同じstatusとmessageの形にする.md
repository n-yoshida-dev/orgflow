# ADR-040: 型に変換できない入力には 400 を返し、本文をほかのエラーと同じ status と message の形にする

- Status: Accepted
- Date: 2026-10-12
- 関連: ADR-031（ステータスは次の行動で選ぶ） / ADR-032（文言はハンドラが決める） / ADR-024（400 は本文や URL の形式の誤りに使う） / ADR-017（OpenAPI を契約とする）

> **決定**: API は、届いた本文（JSON）や URL の中の値を、Java の型に変換できないとき（JSON の書き方が壊れている、UUID の欄に UUID の形をしていない文字が入っている など）に 400 を返す。Java の型には変換できたが、自分で決めた入力の決まり（必須・文字数・範囲）に合わないときは、これまでどおり 422 を返す。400 の本文は、ほかのエラーと同じ `status` と `message` の 2 項目の形にし、OpenAPI にも書く。

例：

- `POST /tenants/abc/select`（URL の tenant ID が `abc`）→ `abc` は UUID に変換できないので 400
- `POST /requests` で、組織 ID の欄に `"test"` を送る → UUID に変換できないので 400
- `POST /requests` で、タイトルを空にして送る → 文字列には変換できるが、必須の決まり（`@NotBlank`）に合わないので 422
- 400 の本文は `{ "status": 400, "message": "<固定の文言>" }` の形になる

## 背景

UUID の欄に `test` を送ったときや、URL の ID に `abc` を送ったとき、API は 400 を返していた。この 400 は、自分で書いた例外ハンドラ（`GlobalExceptionHandler`）ではなく、Spring に元からある処理が返していた。

この 400 は OpenAPI のどの API にも書かれていなかった。また、本文の形も、ほかのエラーの `status` と `message` の 2 項目とは違っていた。そのため画面は、OpenAPI に無い番号と、`message` の入っていない本文を受け取っていた。

## 理由

- 「Java の型に変換できない」と「変換できたが自分の決まりに合わない」で分けると、境目が API の中の処理の順番（型への変換の前か後か）と一致する。開発者は、どちらの番号になるかを処理の順番から説明できる
- 「読めない要求は 400」は、HTTP の一般的な使い方に合う。ADR-024 でも、400 は本文や URL の形式の誤りに使うと書いている
- 本文の形をそろえると、画面はエラーの番号に関係なく、同じ `message` の欄から文言を読める
- OpenAPI に書くと、画面を作る人は、API が返しうる番号を OpenAPI だけで確かめられる（ADR-017）

## 検討した他の案

- **案A: 型に変換できない入力も 422 にそろえる** — 画面が見分ける番号は減る。しかし HTTP の一般的な使い方からずれ、ADR-024 の書き方とも食い違う
- **案B: Spring に元からある処理のまま 400 を返し、OpenAPI にも書かない** — 作業は要らない。しかし、OpenAPI に無い番号と、形の違う本文が返り続ける

## 受け入れる制約

- Spring に任せていた 400 を、自分の例外ハンドラで返すようにする。そのため、型の変換に失敗したときの例外の種類が増えたら、開発者がハンドラを足す必要がある
- 400 の文言は 1 つに固定し、どの項目が変換できなかったかは返さない。文言は例外の種類ごとにハンドラが固定で決める、という ADR-032 の決まりに合わせるため。そのため利用者は、400 の本文だけでは、どの欄を直せばよいか分からない

## 見直す条件

- RFC 9457（Problem Details）のような、項目を細かく持つエラーの形式を採用するとき（ADR-031 と同じ）
- どの項目が変換できなかったかを、画面に返す必要が出たとき
