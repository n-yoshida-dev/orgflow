# ADR-017: OpenAPI を API 契約として先に整備し、v1 は重要 endpoint に絞る

- Status: Accepted
- Date: 2026-04-19
- 関連: ADR-016（認証方式）

> **決定**: 実装より先に OpenAPI を API 契約として整備する。v1 では業務フローと RBAC に効く endpoint を優先し、反復的な CRUD は実装の進行に合わせて後から追加する。

## 背景

Phase 1 では、実装に入る前に API の責務整理と OpenAPI の骨子作成を行った。操作の洗い出し、API グループの分類、パス候補の検討を経て `openapi.yaml` を契約として置いている。

一方で、全 endpoint を最初から同じ密度で書こうとすると、業務フローに効く endpoint と単純な CRUD が同じ作業量として並び、契約として先に固めるべき部分が埋もれる。どこまでを v1 の契約に含めるかを決める必要があった。

## 理由

- 実装より先に契約を置くことで、後続の Spring Boot 実装やフロント接続の際に API の形が実装都合でぶれない
- request、approval、tenant membership role、internal organization membership role のように、業務フローと認可の判断が現れる endpoint を先に固めるほうが、後戻りのコストが大きい部分を先に潰せる
- 反復的な CRUD は形が定型で、実装段階で確定させても契約が揺れにくい

## 検討した他の案

- **案A: 実装を先行させ、後から OpenAPI を整備する** — API の形が実装都合で決まり、フロント接続や Go への置き換え時に契約として使えない
- **案B: 全 endpoint を同じ密度で先に OpenAPI 化する** — 反復 CRUD の記述量が大きく、先に固めるべき業務フロー・認可・監査ログの endpoint に時間を割けない

## 受け入れる制約

- v1 の時点では一部の CRUD が契約に載っていない
- 一覧 API の絞り込み条件や 200 / 204 の使い分けなど、一部の設計判断は実装段階での調整が残る
- OpenAPI と実装の不一致を防ぐ仕組みは別途必要になる

## 見直す条件

- 実装を進める中で、未記載の endpoint が主要業務フローに影響し始めたとき
- React 接続や Go への置き換えの段階で、契約不足により実装が詰まるとき
- OpenAPI から型生成や自動テスト連携を行う段階に進むとき
