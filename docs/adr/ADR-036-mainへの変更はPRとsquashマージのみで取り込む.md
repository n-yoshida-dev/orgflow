# ADR-036: main への変更は PR と squash マージのみで取り込む

- Status: Accepted
- Date: 2026-08-25
- 関連: ADR-033（必須チェックが実行するテストの戦略）

> **決定**: main ブランチを保護し、直接の push を禁止する。変更は必ず PR を経由し、CI のチェック合格と main への追従（up-to-date）を必須とする。マージ方式は squash のみとし、main の履歴を「1 PR = 1 コミット」に保つ。main への force push と削除も禁止する。

## 背景

一人開発では main へ直接 push できてしまう。CI を整備しても、必須チェックは PR に対して働くため、直接の push は CI を迂回でき、テストが落ちる変更が main に入りうる。「気をつける」という運用ではなく、設定で保証するかどうかを決める必要があった。

また、マージ方式が途中から merge commit と squash で混在し、main の履歴の形が PR ごとに違っていた。どちらかに固定するかも決める必要があった。

## 理由

- PR 必須にして初めて「テストが通らない変更は main に入らない」が強制になる。直接 push を残す限り、CI は迂回できる抜け道つきの検問でしかない
- up-to-date 必須により、マージ直前の main との組み合わせでチェックが走る。2つの PR が個別には緑でも、合流すると壊れるケースを防げる
- squash のみに固定すると main の履歴が変更単位（PR 単位）で読める。PR 内の試行錯誤のコミットは PR 側に残るため、失われない
- force push と削除の禁止により、公開済みの履歴が後から書き換わらないことを保証する

## 検討した他の案

- **案A: 保護せず、運用ルールとして「PR を経由する」と決めるだけにする** — 設定が不要で、一人開発なら手間も最小。しかし、うっかり直接 push したときに止まらず、守れていることの保証がどこにもない
- **案B: PR は必須にするが up-to-date は必須にしない** — main が動くたびに PR を更新して CI を再実行する手間が消える。しかし個別に緑の PR 同士が合流して壊れる隙間が残り、「main は常にテストが通る」と言い切れなくなる
- **案C: マージ方式を merge commit にする** — PR 内のコミット単位の履歴が main にそのまま残り、複数人開発で個々の変更を追うには有利。しかし一人開発のポートフォリオでは、main を変更単位で読める方が履歴の価値が高い

## 受け入れる制約

- 一行の修正でも、ブランチ作成 → PR → CI 完了待ち → マージの手順を踏む
- main が進むたびに、開いている PR は main の取り込みと CI の再実行が必要になる
- PR 内のコミット単位の履歴は main に残らない（PR ページで参照する）

## 見直す条件

- 複数人での開発になり、承認レビューの必須化や、コミット単位の履歴を main に残す必要が出た場合
- CI の実行時間が延び、up-to-date 必須による再実行が開発の律速になった場合
