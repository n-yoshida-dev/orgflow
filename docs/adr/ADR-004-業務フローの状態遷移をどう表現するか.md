# ADR-004: 業務フローの状態遷移は明示的な状態モデルで表現する

- Status: Accepted
- Date: 2026-03-19

## 背景

- 申請・承認フローでは、request がどの状態にあるかが業務上の中心になる
- ステータスを曖昧に扱うと、次の問題が発生する
  - 不正な状態遷移
  - 承認ロジックの分散
  - 下書きと申請中の区別が曖昧になる
  - 差し戻し後の再申請時に履歴の意味が崩れる
- Phase 1 では、単純な CRUD ではなく、申請 → 承認 / 差し戻し / 却下 → 監査ログ記録の一貫した業務フローを説明できる必要がある

## 採用した案

request の状態を明示的な `request_status` と遷移ルールで表現する。

Phase 1 で扱う request_status は次の 6 つとする。

- `draft`
- `in_progress`
- `approved`
- `returned`
- `rejected`
- `cancelled`

また、差し戻し後の再申請では既存 request を更新せず、
新しい request を作成する。

## 採用理由

- `draft` を独立させることで、下書き保存と申請中を分けて扱える
- `in_progress` を「申請済みで承認フロー中」の状態としてまとめることで、Phase 1 の状態数を増やしすぎずに済む
- `returned` の request を上書きせず、新版 request を作ることで、差し戻し前後の履歴を説明しやすい
- request の現在状態は request 側に集約し、approval は判断履歴に限定することで、責務を分けられる
- 状態遷移を固定することで、API・認可・監査ログ・テストを同じ前提で設計できる

## 具体的な状態遷移

Phase 1 では、最低限次の遷移を認める。

- `draft` → `in_progress`
- `draft` → `cancelled`
- `in_progress` → `approved`
- `in_progress` → `returned`
- `in_progress` → `rejected`
- `in_progress` → `cancelled`

差し戻し後の再申請は、
`returned` を `in_progress` に戻すのではなく、
**新しい request を作成する** ことで表現する。

そのため、旧版 request は `returned` のまま残る。

## 補足ルール

- `draft` では `amount = 0` を許容する
- `draft` から `in_progress` へ遷移する時点では、0 円申請は不正として扱う
- `approved` / `returned` / `rejected` / `cancelled` では、`current_applied_approval_route_step_id` は `NULL` とする
- approval は request の状態そのものではなく、承認・差し戻し・却下の判断履歴として扱う

## 不採用案

### 案A: ステータスを自由更新する

- 不採用理由
  - 不正な状態遷移が発生しやすい
  - どの操作が許されるかを一貫して説明しにくい

### 案B: 下書きと申請中を同じ状態で扱う

- 不採用理由
  - 0 円下書きのような暫定状態と、承認フロー中の正式状態が混ざる
  - 入力検証や業務ルールが曖昧になる

### 案C: 差し戻し後に既存 request を更新して再利用する

- 不採用理由
  - 差し戻し前の申請内容が失われる
  - 監査ログや履歴説明との整合が悪くなる
  - request の版管理方式と矛盾する

### 案D: `submitted` を独立状態として追加する

- 不採用理由
  - Phase 1 では `in_progress` と役割が近く、状態数だけが増える
  - 現時点のユースケースでは、申請済みかつ承認フロー中であることを `in_progress` で十分表現できる

## 受け入れる制約

- 状態定義と遷移定義の設計コストがかかる
- 差し戻し再申請を新規 request 作成で表現するため、系列単位での取得が必要になる
- `submitted` を分けないため、「申請直後」と「途中段承認待ち」は同じ `in_progress` で扱う

## 見直す条件

- ワークフローが複雑化し、`in_progress` の中をさらに分ける必要が出た場合
- 申請受付、審査中、保留など、業務上意味の異なる中間状態が増えた場合
- ワークフローエンジンや状態機械ライブラリを導入する場合
