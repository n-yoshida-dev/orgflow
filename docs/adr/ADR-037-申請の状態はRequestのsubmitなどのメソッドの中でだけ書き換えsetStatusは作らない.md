# ADR-037: 申請の状態は Request の submit などのメソッドの中でだけ書き換え、setStatus は作らない

- Status: Accepted
- Date: 2026-10-11
- 関連: ADR-004（状態と遷移の表） / ADR-031（不正な遷移は 409） / ADR-035（状態列は text と CHECK 制約） / ADR-039（submit の判定順序）

> **決定**: 申請の状態（`requests.status` 列の値。`draft`・`in_progress` など）を書き換えられるのは、`Request` クラスが持つ操作ごとのメソッドだけにする。操作は提出（`submit()`）・承認・差し戻し・却下・取り下げの 5 つ。各メソッドは、状態を書き換える前に「今の状態からこの操作をしてよいか」を確かめ、してはいけない場合は例外を投げる（API はこの例外を 409 で返す）。`Request` クラスには、状態を好きな値に書き換えられる `setStatus()` を作らない。

例：申請を提出するとき

- Service は `request.submit()` を呼ぶ
- `submit()` の中で、`Request` は自分の状態が `draft` かを確かめる。`draft` なら、状態を `in_progress` に書き換える
- 状態がすでに `in_progress` なら（ボタンの連打で 2 回目の提出が届いたときなど）、`submit()` は例外を投げ、API は 409 を返す
- Service に `request.setStatus("in_progress")` と書くことはできない（`setStatus()` が無いため）

## 背景

submit の実装を始めるにあたり、ADR-004 で決めた状態の表（例：`draft` の申請は `in_progress` か `cancelled` にしか変えられない）を、どのクラスのコードで確かめるかを決める必要があった。

Phase 1 では、提出に続いて承認・差し戻し・却下・取り下げも作る。5 つの操作のどれも、操作の前に「今の状態でこの操作をしてよいか」を確かめなければならない。

この判断をした時点の `Request` クラスは、作成時（`createDraft()`）に状態を `draft` にするだけで、作成後に状態を書き換えるメソッドを 1 つも持っていなかった。

## 理由

- `setStatus()` が無ければ、状態を書き換える方法は、確かめの入った 5 つのメソッドだけになる。`setStatus()` があると、確かめを書き忘れた Service のメソッドからでも、`draft` の申請を `approved` にするような書き換えができてしまう
- 状態の規則が `Request` クラス 1 か所に集まる。承認や差し戻しを足すときも、開発者は `Request` クラスを読めば規則を全部確かめられる
- 状態の規則のテストを、mock を使わずに `Request` だけで書ける。`createDraft()` が状態を `draft` にすることを確かめるテストと同じ書き方になる
- 作成時の状態（`draft`）も、`createDraft()` の中で `Request` 自身が決めている。状態を決めるのは常に `Request`、という形でそろう
- Service の仕事が「申請を DB から読む → 権限を確かめる → `submit()` などを呼ぶ → 保存する」の 4 手順だけになり、Service のコードが短くなる

## 検討した他の案

- **案A: Service に if 文で規則を書き、`Request` に `setStatus()` を足す** — 例：Service の submit 処理に「状態が `draft` でなければ例外」と書いてから `request.setStatus("in_progress")` を呼ぶ。よく見る書き方で、変更する量も少ない。採らなかった理由は 2 つ。1 つ目は、`setStatus()` があると、if 文を書き忘れた Service のメソッドからも状態を書き換えられること。2 つ目は、規則が Service の 5 つのメソッドに分かれて書かれ、全体を確かめるには 5 か所を読む必要があること
- **案B: 状態を Java の enum にし、ADR-004 の表（どの状態からどの状態へ移れるか）を enum の中に一覧で持たせる** — 表が 1 か所にそのまま写るのは利点。採らなかった理由は、今の `Request` は状態を `String` で持っており、enum に変える作業が増えるため。案B は「メソッドの中で何を見て確かめるか」を変えるだけなので、`setStatus()` を作らないというこの決定とは両立する。規則が増えて必要になった時点で案B に移ればよい

## 受け入れる制約

- 各メソッドの中に、その操作をしてよい状態（例：提出なら `draft` だけ、取り下げなら `draft` と `in_progress`）を書く。そのため ADR-004 の表は、コードの中では 5 つのメソッドに切り分けられて書かれ、表の形のまま 1 か所には並ばない。開発者が ADR-004 の表を変えたときは、関係するメソッドを 5 つの中から探して直す必要がある（案B なら enum の 1 か所を直せばよい）
- `Request` クラスは「DB の 1 行の値を持つだけの入れ物」ではなくなり、業務の規則（どの状態からどの操作ができるか）も持つ。`Request` を入れ物として扱う書き方に慣れた開発者には、見慣れない形になる

## 見直す条件

- 操作が増えて、各メソッドに書いた規則と ADR-004 の表が食い違い始めたとき（案B の enum に移る）
- 状態を変えてよいかの判断に、`Request` 以外のデータが必要になったとき。例：承認のあと `approved` にするか次の段へ進めるかは、承認ルートの写し（ADR-008）を読んで最後の段かどうかを見ないと決められない。この判断を `Request` の中だけで行えない場合は、確かめる場所を考え直す
