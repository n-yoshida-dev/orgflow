# ADR-003: role は組織への所属に付与し、操作権限のみを表す

- Status: Accepted
- Date: 2026-03-19
- 関連: ADR-025（role の保存構造） / ADR-014（権限スコープの分離） / ADR-012（approval_policy と approval_route）

> **決定**: role は user 単体ではなく組織への所属に対して付与し、role が表すのは操作権限だけとする。役職や承認条件は role に含めない。

## 背景

organization / role / request / approval / audit_log を扱う構成では、次の3つが混同されやすい。

- 役職（部長、課長といった肩書き）
- 承認ルート（誰が承認するか）
- 操作権限（何ができるか）

この3つを1つの概念で表すと、異動や兼務のたびに承認ルートまで壊れる。何を role に含めるかを最初に決める必要があった。

## 理由

- 同じ user でも所属する組織ごとに権限を変えられる。兼務している user が、組織 A では申請でき、組織 B ではできない、といった状態を表せる
- 承認ルートの決定ロジックを `approval_policy` に集約でき、role を変えても承認ルートが影響を受けない
- 異動は所属関係の変更として表せるため、role 定義そのものを触らずに済む

## 検討した他の案

- **案A: 役職をそのまま認可に使う** — 異動・兼務・例外対応のたびに役職の意味を拡張することになる。「課長だが承認権限は持たない」といった状態を表せない
- **案B: role に承認条件を含める** — role が「何ができるか」と「誰が承認するか」の両方を持ち、承認ルートを変えるだけで操作権限まで変わってしまう

## 受け入れる制約

- 概念数が増える。user、組織、所属、role の4つを理解しないと権限を追えない
- 権限を確認するのに所属関係を経由するため、参照が1段深くなる

## 見直す条件

- 代理承認や閲覧専用権限など、操作権限で表しきれない権限が必要になった場合
- role と approval_policy の責務分担を再整理する必要が出た場合
- permission ベースのより細かい認可モデルへ移行する場合
