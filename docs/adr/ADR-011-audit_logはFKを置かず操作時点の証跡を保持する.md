# ADR-011: audit_log は対象に FK を置かず、操作時点の証跡を保持する

- Status: Accepted
- Date: 2026-03-25
- 関連: ADR-002（監査ログを独立させる方針）

> **決定**: 操作対象は `target_type` と `target_id` の2列で保持し、`target_id` に外部キー制約は置かない。操作主体は `user_id` / `actor_organization_id` に加え、操作時点の表示用スナップショット（`actor_user_display_name` / `actor_user_mail_address` / `actor_organization_name`）を保持する。

## 背景

audit_log は request・approval・user・approval_policy など複数の種別を横断して操作を記録する。対象の種別が固定されていないため、単一の外部キーでは参照先を表せない。

また監査ログは、機械的に追跡できるだけでなく、人が後から読んで「誰が・どの組織で・何に対して・何をしたか」を理解できる必要がある。参照先のレコードが削除されたり、表示名が変更されたりしたあとに、記録が読めなくなってはいけない。

## 理由

- 監査ログは操作時点の不変な証跡であり、対象レコードが後から削除されても記録が失われてはいけない。外部キーを置くと、削除時に制約エラーになるか、削除自体を禁止することになる
- `target_type` と `target_id` を分けることで、`WHERE target_type = 'request' AND target_id = ?` のような対象別の検索が書ける
- 操作主体を ID だけで持つと、監査画面で人が読めない。表示名だけで持つと、同名の利用者や表示名変更後の照合ができない
- そのため操作主体は、ID による追跡性と、表示用スナップショットによる可読性の両方を持たせる。スナップショットは親テーブルの値が変わっても更新しない。操作時点の状態を残すことが目的だから

## 検討した他の案

- **案A: 各対象テーブルへの外部キー制約を持つ** — 参照先の削除時に制約エラーになるか、削除を禁止しすぎる。監査ログが不変な証跡であるという性質と両立しない
- **案B: 対象種別と識別子を1列にまとめる（`request:uuid` など）** — WHERE 句での検索が扱いにくく、インデックス設計も不自然になる
- **案C: 操作主体を表示名やメールアドレスだけで持つ** — 同名利用者や表示名変更後の追跡ができない
- **案D: 操作主体を ID だけで持つ** — 監査画面で読めず、操作時点の所属や表示名が分からない

## 受け入れる制約

- `target_id` の参照整合性を DB が保証しない。存在しない id を書き込んでも防げない
- 操作主体について ID とスナップショットの両方を持つため、列数が増える
- スナップショットは親テーブルの値が変わっても自動更新されない（意図した動作だが、現在値と食い違う）
- users / organizations の削除戦略によっては、操作主体側の外部キーの扱いを再整理する必要がある

## 見直す条件

- 監査ログの検索要件が複雑化し、対象種別ごとに専用テーブルを持つほうが有利になった場合
- 外部 IdP 連携により操作主体の保持方法を再整理する必要が生じた場合
- 物理削除の方針を見直す場合
