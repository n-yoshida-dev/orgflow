# ADR-004: 業務フローの状態遷移を明示的な状態モデルで表現する

- Status: Accepted
- Date: 2026-03-19
- 関連: ADR-007（request の版管理） / ADR-008（承認ルートの適用）

> **決定**: request の状態を `request_status` と遷移ルールで明示的に表現する。差し戻し後の再申請では既存 request を更新せず、新しい request を作成する。

Phase 1 で扱う状態と、認める遷移は次のとおり。

| 状態 | 意味 | 遷移先 |
|---|---|---|
| `draft` | 下書き | `in_progress` / `cancelled` |
| `in_progress` | 申請済みで承認フロー中 | `approved` / `returned` / `rejected` / `cancelled` |
| `approved` | 承認完了 | なし |
| `returned` | 差し戻し | なし（再申請は新しい request） |
| `rejected` | 却下 | なし |
| `cancelled` | 取り下げ | なし |

## 背景

申請・承認フローでは、request がどの状態にあるかが業務の中心になる。状態を自由に更新できる設計にすると、次の問題が起きる。

- 承認されていない request が承認済みになるなど、不正な遷移を防げない
- どの操作が許されるかの判定が各所に分散する
- 下書きと申請中の区別が曖昧になり、入力検証の基準が定まらない
- 差し戻し後に上書きすると、差し戻し前に何を申請していたのかが失われる

## 理由

- `draft` を独立させることで、下書き保存と申請中を別の状態として扱え、入力検証の基準を分けられる
- `in_progress` を「申請済みで承認フロー中」としてまとめることで、Phase 1 の状態数を抑えられる
- `returned` の request を上書きせず新しい版を作ることで、差し戻し前後の申請内容が両方残る
- 現在状態は request 側に集約し、approval は判断の履歴に限定することで、責務が分かれる
- 遷移を固定することで、API・認可・監査ログ・テストが同じ前提で書ける

## 付随して決めたルール

- `draft` では `amount = 0` を許容するが、`in_progress` へ遷移する時点では 0 円申請を不正として扱う
- `approved` / `returned` / `rejected` / `cancelled` では `current_applied_approval_route_step_id` を `NULL` とする
- approval は request の状態そのものではなく、承認・差し戻し・却下の判断履歴として扱う

## 検討した他の案

- **案A: ステータスを自由に更新できるようにする** — 不正な遷移を防げず、どの操作が許されるかを一貫して説明できない
- **案B: 下書きと申請中を同じ状態で扱う** — 0 円下書きのような暫定状態と承認フロー中の正式な状態が混ざり、入力検証の基準が定まらない
- **案C: 差し戻し後に既存 request を更新して再利用する** — 差し戻し前の申請内容が失われ、版管理の方針（ADR-007）とも矛盾する
- **案D: `submitted` を独立した状態として追加する** — `in_progress` と役割が近く、現時点のユースケースでは状態数が増えるだけになる

## 受け入れる制約

- 状態定義と遷移定義の設計コストがかかる
- 差し戻し再申請を新規 request で表すため、1つの申請を追うには系列単位での取得が必要になる
- 「申請直後」と「途中段の承認待ち」を区別できない。どちらも `in_progress` になる

## 見直す条件

- ワークフローが複雑化し、`in_progress` の中をさらに分ける必要が出た場合
- 申請受付、審査中、保留など業務上意味の異なる中間状態が増えた場合
- ワークフローエンジンや状態機械ライブラリを導入する場合
