# ADR-040: 読めない入力は 400 とし、応答本文を他のエラーと同じ形にそろえる

- Status: Accepted
- Date: 2026-10-12
- 関連: ADR-031（次の行動で選ぶ） / ADR-032（文言はハンドラが決める） / ADR-024（400 は body や path の形式不正に寄せる） / ADR-017（OpenAPI を契約とする）

> **決定**: 要求の本文や URL の値を、受け取る型に変換できない場合（JSON が壊れている、UUID の形をしていない等）は 400 を返す。変換はできたが入力の決まり（必須・文字数・範囲）に合わない場合は、従来どおり 422 とする。400 の応答本文は他のエラーと同じ形（ステータスと文言）にそろえ、OpenAPI に記載する。

## 背景

UUID を受け取る項目に `test` を送った場合や、URL の識別子に `abc` を送った場合、フレームワーク既定の処理が 400 を返していた。

この 400 は OpenAPI のどの endpoint にも書かれておらず、本文の形も他のエラー（ステータスと文言）と異なっていた。クライアントは、契約にない番号と、文言の入っていない本文を受け取ることになる。

## 理由

- 「読めない（型に変換できない）」と「読めたが決まりに合わない」で分けると、境目が処理の段階（型への変換の前か後か）と一致し、説明しやすい
- 一般的な HTTP の使い方（読めない要求は 400）に沿う。ADR-024 でも、400 を body や path の形式不正に寄せると書いている
- 本文の形をそろえると、クライアントはエラーの番号に関係なく、同じ項目から文言を読める
- 契約に書くことで、クライアントが受け取りうる番号を OpenAPI だけで把握できる（ADR-017）

## 検討した他の案

- **案A: 読めない入力も 422 にそろえる** — クライアントが区別する番号は減るが、一般的な使い方からずれ、ADR-024 の記述とも食い違う
- **案B: フレームワーク既定のまま、契約にも書かない** — 作業は要らないが、契約にない番号と、形の違う本文が返り続ける

## 受け入れる制約

- フレームワーク既定の処理に任せていた 400 を自前のハンドラで返すため、型の変換に失敗する例外の種類が増えたときは、ハンドラを足す必要がある
- 400 の文言は固定とし、どの項目が読めなかったかは返さない

## 見直す条件

- RFC 9457（Problem Details）のような構造化されたエラー形式を採用する場合（ADR-031 と同じ）
- どの項目が読めなかったかをクライアントに返す必要が出た場合
