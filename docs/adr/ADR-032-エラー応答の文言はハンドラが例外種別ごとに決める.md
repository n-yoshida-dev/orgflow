# ADR-032: エラー応答の文言はハンドラが例外種別ごとに決め、例外のメッセージは応答に含めない

- Status: Accepted
- Date: 2026-08-22
- 関連: ADR-031（HTTP ステータスの選び方） / ADR-017（OpenAPI を契約とする）

> **決定**: 業務上のエラーは種別ごとの例外として Service から投げ、HTTP ステータスと応答の文言は共通のハンドラが例外種別ごとに固定で決める。例外に渡したメッセージは応答に含めず、サーバーのログにのみ記録する。

## 背景

Service はエラーの種別ごとに例外を投げ、共通のハンドラがそれを HTTP 応答に変換している。このとき、Service が例外に渡したメッセージをそのまま応答に載せるのか、ハンドラが固定の文言を返すのかが決まっていなかった。

現状はハンドラが固定文言を返しており、Service 側で例外に渡したメッセージはどこにも出ていない。この状態を「そういう設計」として確定させるか、メッセージを応答に出す方向に変えるかを決める必要があった。

## 理由

- 応答の文言が一箇所に集まり、OpenAPI の契約（ADR-017）と突き合わせやすい。Service の各所に散ると契約との食い違いに気づけない
- Service は HTTP を知らずに済む。例外種別を投げるだけで、ステータスや文言の決定はハンドラに閉じる
- 例外のメッセージは開発者向けの情報（どの判定で落ちたか、識別子は何か）を含みうる。応答に出すと内部の構造や他 tenant の情報が漏れる経路になる
- 例外のメッセージを捨てずにログへ記録すれば、利用者には固定文言、開発者には詳細、という分担になる

## 検討した他の案

- **案A: 例外のメッセージをそのまま応答に返す** — Service を書くたびに文言を決められて手軽だが、文言が分散して契約と乖離し、内部情報が漏れる経路になる
- **案B: 例外クラス自身に HTTP ステータスと文言を持たせる** — ハンドラが薄くなるが、例外（業務の失敗）が HTTP（表現の都合）を知ることになる。Service を HTTP 以外から呼ぶ場面で不自然になる
- **案C: 例外にメッセージを渡さない（引数なし）** — 捨てられる情報を最初から作らないという点で一貫するが、ログに残せる手がかりも失う

## 受け入れる制約

- 応答の文言は例外種別ごとに1つしか持てない。同じ種別で状況により文言を変えたい場合は、種別を分ける必要がある
- 新しい例外種別を追加するたびに、ハンドラ側にも対応を追加する必要がある。追加を忘れると既定の 500 になる
- 例外のメッセージをログに記録する責務がハンドラに乗る

## 見直す条件

- RFC 9457（Problem Details）のような構造化エラー形式を採用し、エラー種別やフィールド単位の詳細を本文で返す必要が出た場合
- 多言語対応で、文言をハンドラに固定で持てなくなった場合
- 例外種別が増え、ハンドラへの対応追加が漏れやすくなった場合
