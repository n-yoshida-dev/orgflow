# ADR-038: Phase 1 の submit では、申請の組織と種別だけで承認ルールを選び、見つからなければ 500 を返す

- Status: Accepted
- Date: 2026-10-12
- 関連: ADR-008（submit 時に承認ルートを決めて申請ごとに保存する） / ADR-009（写しの 3 層） / ADR-012（承認ルールが承認ルートを指す） / ADR-031（到達しないはずの分岐は 500）

> **決定**: API は submit のとき、承認ルール（`approval_policies` の 1 行。「どの組織の、どの種別の申請なら、どの承認ルートを使うか」）を、申請の組織と申請種別の 2 つが一致するかだけで選ぶ。承認ルールが持つ金額の条件（`min_amount`）は、Phase 1 では選ぶときに使わない。一致する承認ルールが 1 つも無ければ、API は 500 を返す。

例：経理部の申請を submit したとき

- 交通費の申請 → 承認ルール「経理部・交通費」が選ばれ、そのルールが指す承認ルート（1 段）を申請に写す
- 出張費の申請 → 承認ルール「経理部・出張費」が選ばれ、承認ルート（2 段）を写す
- 金額が 1,000 円でも 100 万円でも、選ばれる承認ルールは同じ
- 経理部に「備品購入」の承認ルールを登録し忘れていたら、備品購入の申請の submit は 500 になる

## 背景

ADR-008 で、API は submit のときにどの承認ルートを使うかを決め、その道順を申請ごとに写して保存すると決めた。どの承認ルートを使うかは承認ルールが決める。承認ルールは、組織・申請種別・下限金額の 3 つの条件と、使う承認ルートを持つ。

しかし、承認ルールと承認ルートのテーブルは、設計図（ER 図）にあるだけで、DB にはまだ作られていなかった。Phase 1 の残り期間で submit と approve を動かす必要があるため、開発者は、承認ルールの選び方をどこまで作るかと、一致する承認ルールが無いときに API が何を返すかを決める必要があった。

あわせて、作るテーブルは設計どおりの 7 つ（ルール側の `approval_policies`・`approval_routes`・`approval_route_steps`・`approval_route_step_approvers`、写し側の `applied_approval_routes`・`applied_approval_route_steps`・`applied_approval_route_step_approvers`）とする。

## 理由

- テーブルを設計どおりに作るので、ADR-008・009・012 を書き換えずに済む。また、「submit したあとに承認ルールを変えても、submit 済みの申請の承認ルートは変わらない」を、DB の実際の行で見せられる
- 選び方を一番簡単な形（組織と種別が一致するか）から作り始められる。`min_amount` の列はテーブルに最初から作っておくので、金額の条件はあとから、テーブルを変えずに足せる
- Phase 1 の初期データ（seed）では、申請を作れる組織のすべての申請種別に承認ルールを 1 つずつ登録する。そのため、利用者が普通に操作している限り、「一致する承認ルールが無い」は起きない。これは ADR-031 の「到達しないはずの分岐は 500」に当たる
- 一致する承認ルールが無いことを 4xx で返すと、承認ルールの登録漏れ（サーバー側の設定の問題）が、利用者の入力の誤りとして扱われる。500 なら、サーバー側のエラーとして監視で気づける

## 検討した他の案

- **案A: 組織・種別・金額の 3 つで承認ルールを選ぶ（設計どおりすべて）** — 金額で承認ルートが変わる仕組みは、Phase 1 で見せたい流れ（submit → approve）の説明には要らない。作るコードと初期データの量が増える
- **案B: 写し側の 3 テーブルだけを作り、承認ルート（誰がどの順に承認するか）はコードに直接書く** — 作業は一番少ない。しかし承認者を変えるたびにコードを書き換える必要があり、ADR-008 の「submit のときにルールから決める」も書き換えることになる
- **案C: 一致する承認ルールが無いときは 422 を返す** — 422 は利用者に「入力を直せば通る」と伝える。しかし利用者が直せる入力は無い。承認ルールを登録するのは管理者である

## 受け入れる制約

- 同じ組織・同じ種別に、金額だけが違う承認ルールを 2 つ登録しても、Phase 1 の API はどちらを使うか区別できない。そのため、初期データでは組織・種別ごとに承認ルールを 1 つだけ登録する
- 一致する承認ルールが無いと 500 になるので、開発者が組織や申請種別を増やすときは、承認ルールの登録漏れに気をつける必要がある

## 見直す条件

- 金額によって承認ルートを変える必要が出たとき（`min_amount` を選ぶ条件に加える）
- 管理画面などで、利用者が自分で組織や申請種別を追加できるようになったとき（利用者の操作で「一致する承認ルールが無い」が起きうるため）
