# ADR-016: 認証方式の選定理由

- Status: Accepted
- Date: 2026-04-19

## 背景

- OrgFlow Phase 1 では、ログイン済み API を成立させた上で、認証と認可を分けて説明できる状態を作る必要がある。
- このチャットでは、`/login` と認証必須 API の OpenAPI 記述を進める中で、認証方式をどう表現するかを具体化した。
- Phase 1 の主目的は、認証基盤そのものを深掘りすることではなく、認証済み API、RBAC、業務フロー、監査ログを含むバックエンドの基盤を説明可能にすることである。

## 採用した案

- Phase 1 では、Bearer token を用いる認証済み API として設計し、OpenAPI でも `bearerAuth` を用いて契約として表現する。

## 採用理由

- React や Go への後続フェーズに接続しやすい。
- OpenAPI 上で、認証必須 API と認証不要 API（`/login`）の違いを明示しやすい。
- 「ログイン済み API を成立させる」という Phase 1 の目的に対して、説明可能性と学習コストのバランスがよい。
- セッション認証のようにサーバー側状態の説明を厚く持ち込まずに、API 契約、認可、RBAC、監査ログの論点へ進みやすい。

## 不採用案

- 案A: セッションベース認証
  Phase 1 の API 契約整理と React 接続の説明に対して、状態管理や Cookie 周辺の説明コストが増えるため採らなかった。

- 案B: 外部 IdP 前提の認証
  実務では重要だが、Phase 1 の目的に対しては認証基盤側の論点が重く、今の段階では過剰であるため採らなかった。

## 受け入れる制約

- Bearer token の失効、更新、保管戦略までは Phase 1 で深掘りしない。
- JWT の細かな署名・期限管理や refresh token 戦略は、今は最小限の説明に留める。
- 認証基盤の本格設計ではなく、「認証済み API を前提に認可と業務フローを説明できること」を優先する。

## 見直す条件

- Phase 2 以降で React フロントエンドと接続し、トークン更新や保管戦略が実装論点になるとき。
- 外部 IdP 連携や SSO を扱う要件が入るとき。
- セキュリティ要件の強化により、認証方式そのものを比較し直す必要が出たとき。

## 追記: Phase 1 における認証初期実装の最小方針（2026-04-29）

### 決定

Phase 1 の認証初期実装では、まず Spring Security を API 向けの最小構成に寄せる。

具体的には、次の方針とする。

- `/login` は未認証で呼べる API として `permitAll` にする
- `/hello` は疎通確認用として一時的に `permitAll` にする
- `/error` はバリデーションエラーなどの例外処理が Security に遮られないように `permitAll` にする
- それ以外の API は、まず `authenticated` を基本とする
- CSRF は無効化する
- セッションは作成しない前提とし、`SessionCreationPolicy.STATELESS` を使う
- Spring Security のフォームログインは使わない
- `/login` 成功時点では `currentTenantId` は `null` とする
- current tenant の確定は、後続の `POST /tenants/{tenantId}/select` の責務とする

現時点では、`AuthController` と `AuthService` の責務分割までを実装する。

本物の認証処理、DB検索、パスワード照合、JWT生成、Bearer token から `Authentication` を作る処理は、次工程で扱う。

### 理由

OrgFlow Phase 1 では、認証方式そのものを深く作り込むことよりも、ログイン済み API、RBAC、業務フロー、監査ログを説明可能にすることを優先する。

そのため、最初から refresh token、token 失効戦略、外部 IdP、複雑な authority 設計へ進まず、まずは次の順で進める。

1. SecurityConfig で API の入口制御を作る
2. `/login` の DTO と Controller を作る
3. `AuthService` に login ユースケースの置き場を作る
4. その後で DB検索、パスワード照合、TokenService、JWT 認証 filter へ進む

この順にすることで、Controller / Service / Security の責務を混同せずに進めやすくなる。

### 受け入れる制約

- 現時点の `/login` はまだ本物の認証ではない
- `AuthService#login` はまだ仮実装であり、DB検索・パスワード照合・JWT生成は未実装である
- `/hello` は疎通確認用であり、本番機能ではない
- `/error` を `permitAll` にするのは、Spring Security によって例外処理が阻害されることを避けるための初期実装上の対応である
- `currentTenantId` は `/login` では確定させず、`selectTenant` で扱う

### 見直す条件

- JWT 生成と検証を実装する段階に進むとき
- Bearer token から `Authentication` を生成する filter を実装するとき
- `selectTenant` で current tenant 入り token を再発行する段階に進むとき
- broad authority を `SecurityConfig` や `@PreAuthorize` に入れる段階に進むとき
- 外部 IdP や refresh token 戦略を検討する段階に進むとき

## 追記: DB上の users を使ったログイン認証の最小実装（2026-05-09）

### 背景

これまで `/login` は `LoginRequest` を受け取り、`AuthService#login` から `dummy-token` と `currentTenantId = null` を返す仮実装だった。

Phase 1 では最終的に Bearer token を用いた認証済み API として設計するが、現時点では JWT 生成や Bearer token filter へ進む前に、DB 上の `users` テーブルと seed user を使って、loginId / password による本人確認を成立させる必要があった。

### 決定

`/login` の最小認証処理として、次の方針を採用する。

- `User` Entity は `users` テーブルに対応させる
- `UserRepository` は Spring Data JPA の Repository として作成する
- `UserRepository#findByLoginId(String loginId)` で user を検索する
- `AuthService#login` で loginId による user 検索と password 照合を行う
- password 照合には `PasswordEncoder#matches(rawPassword, hashedPassword)` を使う
- user が存在しない場合も、password が一致しない場合も、同じ `AuthenticationFailedException` として扱う
- `GlobalExceptionHandler` で `AuthenticationFailedException` を 401 Unauthorized に変換する
- 外部レスポンスでは、loginId 未存在と password 不一致を区別しない
- 成功時は、現時点では引き続き `dummy-token` と `currentTenantId = null` を返す
- JWT 生成、Bearer token filter、current tenant 入り token の再発行は後続フェーズへ送る

### 採用理由

loginId 未存在と password 不一致を区別して返すと、外部に「その loginId が存在するかどうか」を推測される可能性がある。

そのため、どちらの場合も外部には同じ 401 と同じメッセージを返す方針にした。

また、`/login` の本人確認処理は `AuthService` の責務とし、`UserRepository` は DB 上の user 検索に限定した。これにより、Repository に認証判断を混ぜず、Controller / Service / Repository の責務を分けたまま進められる。

`PasswordEncoder` は `PasswordConfig` で Bean 化し、`AuthService` にはコンストラクタインジェクションで注入する。これにより、password 照合処理を Spring Security の `PasswordEncoder` に寄せ、BCrypt hash の直接比較や復号のような誤った実装を避ける。

### 受け入れる制約

- 成功時の `accessToken` はまだ本物の JWT ではない
- `currentTenantId` は `/login` 時点では確定せず、引き続き `null` とする
- 認証済み API としての完全な成立には、JWT 生成、Bearer token filter、SecurityContext 連携が別途必要である
- user の tenant 所属、role、current tenant 判定はまだ扱わない
- login 成功 / 失敗の監査ログ記録は未実装であり、監査ログ実装時に再検討する

### 見直す条件

- JWT 生成処理を導入する場合
- Bearer token から Spring Security の `Authentication` を構築する場合
- `POST /tenants/{tenantId}/select` により current tenant 入り token を再発行する場合
- 外部 IdP や Cognito などへ認証基盤を移行する場合
- login 成功 / 失敗を監査ログとして記録する場合

## 追記: `/login` 成功時に JWT access token を発行する（2026-05-12）

### 背景

これまで `/login` は、DB 上の `users` テーブルと seed user を使って loginId / password の本人確認を行っていた。

ただし、認証成功時の `accessToken` は `dummy-token` のままだった。

Phase 1 では最終的に Bearer token を用いた認証済み API として成立させる必要があるため、次の段階として、`/login` 成功時に署名付き JWT access token を返す必要があった。

一方で、この段階ではまだ Bearer token の検証、Spring Security の `SecurityContext` への認証情報設定、tenant / role を使った認可までは扱わない。

### 決定

`/login` 成功時に、`dummy-token` ではなく、JWT 形式の access token を返す。

JWT生成は次の方針で実装する。

- JWT生成には Spring Security 寄りの `JwtEncoder` / `NimbusJwtEncoder` を使う
- 署名方式は Phase 1 のローカル実装では共通鍵方式の HS256 とする
- secret は Javaコードに直接書かず、`application.yaml` では `${ORGFLOW_JWT_SECRET}` として環境変数から読む
- JWT設定は `JwtProperties` で受け取る
- `JwtEncoder` は `JwtConfig` で Bean 化する
- JWT生成処理は `JwtTokenService` に分離する
- `AuthService` は loginId / password 認証に成功した後、`JwtTokenService#generateAccessToken(userId)` を呼び出す
- JWT の `sub` には `loginId` ではなく `users.id` の UUID を文字列化して入れる
- JWT の claim は最小限として `iss`, `sub`, `iat`, `exp` を扱う
- `/login` 時点では `currentTenantId` は引き続き `null` とする

### 採用理由

JWT生成を `AuthService` に直接書かず、`JwtTokenService` に分離することで、本人確認処理と token 生成処理の責務を分けられる。

`AuthService` の責務は、loginId / password による本人確認と、認証成功後に token 発行処理を呼び出すことである。

`JwtTokenService` の責務は、認証済みユーザーの `userId` を受け取り、`iss`, `sub`, `iat`, `exp` を組み立てて署名付き JWT を生成することである。

`JwtConfig` の責務は、環境変数から取得した secret をもとに `JwtEncoder` Bean を作ることである。

この分割により、以下を分けて説明できる。

- 誰に token を発行してよいか: `AuthService`
- token に何を入れるか: `JwtTokenService`
- どう署名するか: `JwtConfig`
- JWT設定をどう受け取るか: `JwtProperties`

また、JWT の `sub` に `loginId` ではなく `users.id` を入れることで、ログインID変更やメールアドレスログインへの変更が将来発生しても、token の主体識別を安定させやすい。

JWT の payload は暗号化されておらず中身を読めるため、password、hashed password、メールアドレス、細かい権限情報などは入れない方針とする。

### 不採用案

- 案A: `dummy-token` のまま後続API実装へ進む
  認証済みAPIとして成立させる前提が弱くなり、Bearer token検証やSecurityContext連携へ進みにくいため採らない。

- 案B: JWT専用ライブラリを別途使う
  JWT文字列の生成だけなら簡単だが、後続で Spring Security の Resource Server / JWT検証 / SecurityContext 連携へ進む際に、発行側と検証側の考え方が分断されやすいため採らない。

- 案C: 外部IdPやCognitoにJWT発行を任せる
  実務では自然な選択肢だが、Phase 1 では OAuth2 / OIDC / IdP設定の学習が主役になりすぎるため、現時点では採らない。

- 案D: `AuthService` 内で `JwtEncoder` を直接組み立てる
  本人確認処理とJWT署名設定の責務が混ざるため採らない。

- 案E: JWTの `sub` に `loginId` を入れる
  `loginId` は将来変更される可能性があり、内部的な主体識別子としては `users.id` の方が安定しているため採らない。

### 受け入れる制約

- この段階では、JWTを発行するだけであり、Bearer token を受け取って検証する処理はまだ未実装である
- Spring Security の `SecurityContext` への認証情報設定はまだ未実装である
- `currentTenantId` は `/login` 時点では確定せず、引き続き `null` とする
- tenant 所属、role、current tenant 判定はまだ JWT に含めない
- login 成功 / 失敗の監査ログ記録は未実装である
- secret は短期的には WSL2 の shell 環境変数で渡す
- 後続で API も Docker Compose 管理に寄せる場合は、`.env` から Docker Compose 経由で環境変数を渡す方針に見直す
- test側の `application.yaml` にも JWT 設定が必要である

### 実装方針

実装上の責務分担は次のとおりとする。

- `application.yaml`
  - `jwt.issuer`
  - `jwt.secret`
  - `jwt.access-token-expires-in`
    を設定する

- `JwtProperties`
  - `application.yaml` の `jwt:` 配下の設定値を Java 側で受け取る

- `JwtConfig`
  - `JwtProperties#getSecret()` を使って `SecretKeySpec` を作る
  - `NimbusJwtEncoder` を `JwtEncoder` Bean として登録する

- `JwtTokenService`
  - `UUID userId` を受け取る
  - `sub` に `userId.toString()` を入れる
  - `iss`, `iat`, `exp` を組み立てる
  - `JwsHeader.with(MacAlgorithm.HS256)` でHS256を指定する
  - `JwtEncoder` で署名付きJWTを生成し、`getTokenValue()` を返す

- `AuthService`
  - loginId / password 認証に成功したら `JwtTokenService#generateAccessToken(user.getId())` を呼び出す
  - `LoginResponse(accessToken, null)` を返す

### 見直す条件

- Bearer token の検証処理を実装する場合
- Spring Security の `SecurityContext` へ認証情報を設定する場合
- `POST /tenants/{tenantId}/select` で current tenant 入り token を再発行する場合
- JWT に tenantId や role を含めるか再検討する場合
- refresh token を扱う場合
- 外部IdP / Cognito / Keycloak などへ認証基盤を移行する場合
- API本体も Docker Compose で起動する構成へ寄せる場合
- GitHub Actions CI でJWT secretをどう扱うか整理する場合
