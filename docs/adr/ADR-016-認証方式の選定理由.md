# ADR-016: 認証方式の選定理由

- Status: Accepted
- Date: 2026-04-19

## 背景

- OrgFlow Phase 1 では、ログイン済み API を成立させた上で、認証と認可を分けて説明できる状態を作る必要がある。
- このチャットでは、`/login` と認証必須 API の OpenAPI 記述を進める中で、認証方式をどう表現するかを具体化した。
- Phase 1 の主目的は、認証基盤そのものを深掘りすることではなく、認証済み API、RBAC、業務フロー、監査ログを含むバックエンドの基盤を説明可能にすることである。

## 採用した案

- Phase 1 では、Bearer token を用いる認証済み API として設計し、OpenAPI でも `bearerAuth` を用いて契約として表現する。

## 採用理由

- React や Go への後続フェーズに接続しやすい。
- OpenAPI 上で、認証必須 API と認証不要 API（`/login`）の違いを明示しやすい。
- 「ログイン済み API を成立させる」という Phase 1 の目的に対して、説明可能性と学習コストのバランスがよい。
- セッション認証のようにサーバー側状態の説明を厚く持ち込まずに、API 契約、認可、RBAC、監査ログの論点へ進みやすい。

## 不採用案

- 案A: セッションベース認証
  Phase 1 の API 契約整理と React 接続の説明に対して、状態管理や Cookie 周辺の説明コストが増えるため採らなかった。

- 案B: 外部 IdP 前提の認証
  実務では重要だが、Phase 1 の目的に対しては認証基盤側の論点が重く、今の段階では過剰であるため採らなかった。

## 受け入れる制約

- Bearer token の失効、更新、保管戦略までは Phase 1 で深掘りしない。
- JWT の細かな署名・期限管理や refresh token 戦略は、今は最小限の説明に留める。
- 認証基盤の本格設計ではなく、「認証済み API を前提に認可と業務フローを説明できること」を優先する。

## 見直す条件

- Phase 2 以降で React フロントエンドと接続し、トークン更新や保管戦略が実装論点になるとき。
- 外部 IdP 連携や SSO を扱う要件が入るとき。
- セキュリティ要件の強化により、認証方式そのものを比較し直す必要が出たとき。

## 追記: Phase 1 における認証初期実装の最小方針（2026-04-29）

### 決定

Phase 1 の認証初期実装では、まず Spring Security を API 向けの最小構成に寄せる。

具体的には、次の方針とする。

- `/login` は未認証で呼べる API として `permitAll` にする
- `/hello` は疎通確認用として一時的に `permitAll` にする
- `/error` はバリデーションエラーなどの例外処理が Security に遮られないように `permitAll` にする
- それ以外の API は、まず `authenticated` を基本とする
- CSRF は無効化する
- セッションは作成しない前提とし、`SessionCreationPolicy.STATELESS` を使う
- Spring Security のフォームログインは使わない
- `/login` 成功時点では `currentTenantId` は `null` とする
- current tenant の確定は、後続の `POST /tenants/{tenantId}/select` の責務とする

現時点では、`AuthController` と `AuthService` の責務分割までを実装する。

本物の認証処理、DB検索、パスワード照合、JWT生成、Bearer token から `Authentication` を作る処理は、次工程で扱う。

### 理由

OrgFlow Phase 1 では、認証方式そのものを深く作り込むことよりも、ログイン済み API、RBAC、業務フロー、監査ログを説明可能にすることを優先する。

そのため、最初から refresh token、token 失効戦略、外部 IdP、複雑な authority 設計へ進まず、まずは次の順で進める。

1. SecurityConfig で API の入口制御を作る
2. `/login` の DTO と Controller を作る
3. `AuthService` に login ユースケースの置き場を作る
4. その後で DB検索、パスワード照合、TokenService、JWT 認証 filter へ進む

この順にすることで、Controller / Service / Security の責務を混同せずに進めやすくなる。

### 受け入れる制約

- 現時点の `/login` はまだ本物の認証ではない
- `AuthService#login` はまだ仮実装であり、DB検索・パスワード照合・JWT生成は未実装である
- `/hello` は疎通確認用であり、本番機能ではない
- `/error` を `permitAll` にするのは、Spring Security によって例外処理が阻害されることを避けるための初期実装上の対応である
- `currentTenantId` は `/login` では確定させず、`selectTenant` で扱う

### 見直す条件

- JWT 生成と検証を実装する段階に進むとき
- Bearer token から `Authentication` を生成する filter を実装するとき
- `selectTenant` で current tenant 入り token を再発行する段階に進むとき
- broad authority を `SecurityConfig` や `@PreAuthorize` に入れる段階に進むとき
- 外部 IdP や refresh token 戦略を検討する段階に進むとき

## 追記: DB上の users を使ったログイン認証の最小実装（2026-05-09）

### 背景

これまで `/login` は `LoginRequest` を受け取り、`AuthService#login` から `dummy-token` と `currentTenantId = null` を返す仮実装だった。

Phase 1 では最終的に Bearer token を用いた認証済み API として設計するが、現時点では JWT 生成や Bearer token filter へ進む前に、DB 上の `users` テーブルと seed user を使って、loginId / password による本人確認を成立させる必要があった。

### 決定

`/login` の最小認証処理として、次の方針を採用する。

- `User` Entity は `users` テーブルに対応させる
- `UserRepository` は Spring Data JPA の Repository として作成する
- `UserRepository#findByLoginId(String loginId)` で user を検索する
- `AuthService#login` で loginId による user 検索と password 照合を行う
- password 照合には `PasswordEncoder#matches(rawPassword, hashedPassword)` を使う
- user が存在しない場合も、password が一致しない場合も、同じ `AuthenticationFailedException` として扱う
- `GlobalExceptionHandler` で `AuthenticationFailedException` を 401 Unauthorized に変換する
- 外部レスポンスでは、loginId 未存在と password 不一致を区別しない
- 成功時は、現時点では引き続き `dummy-token` と `currentTenantId = null` を返す
- JWT 生成、Bearer token filter、current tenant 入り token の再発行は後続フェーズへ送る

### 採用理由

loginId 未存在と password 不一致を区別して返すと、外部に「その loginId が存在するかどうか」を推測される可能性がある。

そのため、どちらの場合も外部には同じ 401 と同じメッセージを返す方針にした。

また、`/login` の本人確認処理は `AuthService` の責務とし、`UserRepository` は DB 上の user 検索に限定した。これにより、Repository に認証判断を混ぜず、Controller / Service / Repository の責務を分けたまま進められる。

`PasswordEncoder` は `PasswordConfig` で Bean 化し、`AuthService` にはコンストラクタインジェクションで注入する。これにより、password 照合処理を Spring Security の `PasswordEncoder` に寄せ、BCrypt hash の直接比較や復号のような誤った実装を避ける。

### 受け入れる制約

- 成功時の `accessToken` はまだ本物の JWT ではない
- `currentTenantId` は `/login` 時点では確定せず、引き続き `null` とする
- 認証済み API としての完全な成立には、JWT 生成、Bearer token filter、SecurityContext 連携が別途必要である
- user の tenant 所属、role、current tenant 判定はまだ扱わない
- login 成功 / 失敗の監査ログ記録は未実装であり、監査ログ実装時に再検討する

### 見直す条件

- JWT 生成処理を導入する場合
- Bearer token から Spring Security の `Authentication` を構築する場合
- `POST /tenants/{tenantId}/select` により current tenant 入り token を再発行する場合
- 外部 IdP や Cognito などへ認証基盤を移行する場合
- login 成功 / 失敗を監査ログとして記録する場合

## 追記: `/login` 成功時に JWT access token を発行する（2026-05-12）

### 背景

これまで `/login` は、DB 上の `users` テーブルと seed user を使って loginId / password の本人確認を行っていた。

ただし、認証成功時の `accessToken` は `dummy-token` のままだった。

Phase 1 では最終的に Bearer token を用いた認証済み API として成立させる必要があるため、次の段階として、`/login` 成功時に署名付き JWT access token を返す必要があった。

一方で、この段階ではまだ Bearer token の検証、Spring Security の `SecurityContext` への認証情報設定、tenant / role を使った認可までは扱わない。

### 決定

`/login` 成功時に、`dummy-token` ではなく、JWT 形式の access token を返す。

JWT生成は次の方針で実装する。

- JWT生成には Spring Security 寄りの `JwtEncoder` / `NimbusJwtEncoder` を使う
- 署名方式は Phase 1 のローカル実装では共通鍵方式の HS256 とする
- secret は Javaコードに直接書かず、`application.yaml` では `${ORGFLOW_JWT_SECRET}` として環境変数から読む
- JWT設定は `JwtProperties` で受け取る
- `JwtEncoder` は `JwtConfig` で Bean 化する
- JWT生成処理は `JwtTokenService` に分離する
- `AuthService` は loginId / password 認証に成功した後、`JwtTokenService#generateAccessToken(userId)` を呼び出す
- JWT の `sub` には `loginId` ではなく `users.id` の UUID を文字列化して入れる
- JWT の claim は最小限として `iss`, `sub`, `iat`, `exp` を扱う
- `/login` 時点では `currentTenantId` は引き続き `null` とする

### 採用理由

JWT生成を `AuthService` に直接書かず、`JwtTokenService` に分離することで、本人確認処理と token 生成処理の責務を分けられる。

`AuthService` の責務は、loginId / password による本人確認と、認証成功後に token 発行処理を呼び出すことである。

`JwtTokenService` の責務は、認証済みユーザーの `userId` を受け取り、`iss`, `sub`, `iat`, `exp` を組み立てて署名付き JWT を生成することである。

`JwtConfig` の責務は、環境変数から取得した secret をもとに `JwtEncoder` Bean を作ることである。

この分割により、以下を分けて説明できる。

- 誰に token を発行してよいか: `AuthService`
- token に何を入れるか: `JwtTokenService`
- どう署名するか: `JwtConfig`
- JWT設定をどう受け取るか: `JwtProperties`

また、JWT の `sub` に `loginId` ではなく `users.id` を入れることで、ログインID変更やメールアドレスログインへの変更が将来発生しても、token の主体識別を安定させやすい。

JWT の payload は暗号化されておらず中身を読めるため、password、hashed password、メールアドレス、細かい権限情報などは入れない方針とする。

### 不採用案

- 案A: `dummy-token` のまま後続API実装へ進む
  認証済みAPIとして成立させる前提が弱くなり、Bearer token検証やSecurityContext連携へ進みにくいため採らない。

- 案B: JWT専用ライブラリを別途使う
  JWT文字列の生成だけなら簡単だが、後続で Spring Security の Resource Server / JWT検証 / SecurityContext 連携へ進む際に、発行側と検証側の考え方が分断されやすいため採らない。

- 案C: 外部IdPやCognitoにJWT発行を任せる
  実務では自然な選択肢だが、Phase 1 では OAuth2 / OIDC / IdP設定の学習が主役になりすぎるため、現時点では採らない。

- 案D: `AuthService` 内で `JwtEncoder` を直接組み立てる
  本人確認処理とJWT署名設定の責務が混ざるため採らない。

- 案E: JWTの `sub` に `loginId` を入れる
  `loginId` は将来変更される可能性があり、内部的な主体識別子としては `users.id` の方が安定しているため採らない。

### 受け入れる制約

- この段階では、JWTを発行するだけであり、Bearer token を受け取って検証する処理はまだ未実装である
- Spring Security の `SecurityContext` への認証情報設定はまだ未実装である
- `currentTenantId` は `/login` 時点では確定せず、引き続き `null` とする
- tenant 所属、role、current tenant 判定はまだ JWT に含めない
- login 成功 / 失敗の監査ログ記録は未実装である
- secret は短期的には WSL2 の shell 環境変数で渡す
- 後続で API も Docker Compose 管理に寄せる場合は、`.env` から Docker Compose 経由で環境変数を渡す方針に見直す
- test側の `application.yaml` にも JWT 設定が必要である

### 実装方針

実装上の責務分担は次のとおりとする。

- `application.yaml`
  - `jwt.issuer`
  - `jwt.secret`
  - `jwt.access-token-expires-in`
    を設定する

- `JwtProperties`
  - `application.yaml` の `jwt:` 配下の設定値を Java 側で受け取る

- `JwtConfig`
  - `JwtProperties#getSecret()` を使って `SecretKeySpec` を作る
  - `NimbusJwtEncoder` を `JwtEncoder` Bean として登録する

- `JwtTokenService`
  - `UUID userId` を受け取る
  - `sub` に `userId.toString()` を入れる
  - `iss`, `iat`, `exp` を組み立てる
  - `JwsHeader.with(MacAlgorithm.HS256)` でHS256を指定する
  - `JwtEncoder` で署名付きJWTを生成し、`getTokenValue()` を返す

- `AuthService`
  - loginId / password 認証に成功したら `JwtTokenService#generateAccessToken(user.getId())` を呼び出す
  - `LoginResponse(accessToken, null)` を返す

### 見直す条件

- Bearer token の検証処理を実装する場合
- Spring Security の `SecurityContext` へ認証情報を設定する場合
- `POST /tenants/{tenantId}/select` で current tenant 入り token を再発行する場合
- JWT に tenantId や role を含めるか再検討する場合
- refresh token を扱う場合
- 外部IdP / Cognito / Keycloak などへ認証基盤を移行する場合
- API本体も Docker Compose で起動する構成へ寄せる場合
- GitHub Actions CI でJWT secretをどう扱うか整理する場合

## 追記: JWT access token の Bearer token 検証を Spring Security Resource Server で行う（2026-05-15）

### 背景

前段階では、`/login` 成功時に `dummy-token` ではなく、署名付き JWT access token を返せるようにした。

ただし、その時点では JWT を発行できるだけであり、後続 API に `Authorization: Bearer <JWT>` として送られた token をサーバー側で検証し、認証済み API として扱うところまでは未実装だった。

Phase 1 では、ログイン済み API として成立していることが前提になるため、JWT access token を後続 API の認証情報として利用できる状態にする必要があった。

### 決定

OrgFlow Phase 1 では、JWT access token の検証を Spring Security Resource Server の仕組みに寄せて実装する。

具体的には、次の方針とする。

- `/login`, `/hello`, `/error` は `permitAll` とする
- それ以外の API は `authenticated` とする
- `SecurityConfig` で `oauth2ResourceServer().jwt()` を有効化する
- JWT 検証は Controller / Service の中ではなく、Controller 到達前の Spring Security Filter 側で行う
- `JwtDecoder` は `JwtConfig` で Bean として定義する
- JWT 発行時と同じ `jwt.secret` から `SecretKeySpec` を作成する
- `JwtEncoder` と `JwtDecoder` は同じ secret を使う
- 署名アルゴリズムは、発行側と同じ HS256 とする
- Resource Server が Bearer token を取り出し、`JwtDecoder` が署名・期限などを検証する
- 検証に成功した場合、そのリクエストは Spring Security 上で認証済みとして扱われ、`authenticated()` を通過する

検証用 API として、暫定的に `GET /hello-auth` を追加した。

### 採用理由

Spring Security Resource Server に寄せることで、Bearer token の取り出し、JWT 検証、認証済みリクエストとしての扱いを Spring Security の標準的な流れに乗せられる。

これにより、Controller や Service に JWT 文字列の parse、署名検証、期限チェックなどの責務を持ち込まずに済む。

また、JWT 発行に `JwtEncoder / NimbusJwtEncoder` を使っているため、検証側も `JwtDecoder / NimbusJwtDecoder` を使うことで、Spring Security の認証フローと整合しやすい。

### 不採用案

#### 案A: Controller / Service 内でJWTを手動検証する

不採用理由は、HTTPリクエストの入口で行うべき認証処理が業務処理層に混ざるためである。

Service は、業務ルール、tenant 所属確認、role による認可などを扱う層であり、Bearer token の取り出しや署名検証を担当させると責務が崩れる。

#### 案B: `withJwkSetUri(...)` を使って外部JWK Set URIから鍵を取得する

不採用理由は、現在の OrgFlow は外部 IdP / 認可サーバーを使っていないためである。

今回の JWT は、OrgFlow API 自身が HS256 + secret で発行している。
そのため、検証側も同じ secret を使うべきであり、JWK Set URI を見に行く方式は現時点の構成と合わない。

#### 案C: JJWTなど別ライブラリや独自FilterでJWT検証する

不採用理由は、Spring Security の Resource Server / SecurityContext の流れから外れやすくなるためである。

Phase 1 の目的は、認証基盤そのものを深掘りすることではなく、認証済み API、RBAC、業務フロー、監査ログを含むバックエンド基盤を説明可能にすることである。
そのため、標準的な Spring Security の仕組みに寄せる方が学習コストと説明可能性のバランスがよい。

### 確認済みの挙動

Postman により、以下を確認した。

- JWTなしで `GET /hello-auth` を呼ぶと 401
- 正しいJWTを `Authorization: Bearer <JWT>` として付けると 200
- JWTを1文字削ると 401
- `access-token-expires-in` を一時的に `10s` に変更し、期限切れ後に再実行すると 401
- 設定を元に戻した後、`mvn test` が `BUILD SUCCESS`

### この判断で得られるもの

- `/login` 成功時に発行したJWTを、後続APIの認証情報として利用できる
- `permitAll` と `authenticated` の違いを実装で確認できる
- JWTなし、改ざんJWT、期限切れJWTを拒否できる
- Controller / Service にJWT検証の責務を持ち込まずに済む
- tenant / role による認可へ進む前に、認証済みAPIとしての入口が成立する

### この判断で受け入れる制約

- 現時点では issuer 検証は未実装である
- 現時点では JWT の `sub` から userId を取り出してアプリ側で利用する処理は未実装である
- 現時点では tenant / role による認可は未実装である
- `/hello-auth` は動作確認用の暫定APIであり、今後不要になれば削除または別の保護APIで代替する
- `/login` の loginId / password 認証失敗による 401 と、Spring Security が Controller 到達前に返す 401 は、処理経路が異なる

### 見直す条件

以下の場合は、この判断を見直す。

- `JwtDecoder` に issuer 検証を追加する場合
- `sub` から userId を取り出し、Controller / Service で利用する場合
- `POST /tenants/{tenantId}/select` により current tenant 入り token を再発行する場合
- tenant / role / membership を使った認可へ進む場合
- JWT に tenantId や role を含めるか再検討する場合
- refresh token を扱う場合
- 外部 IdP / Cognito / Keycloak などへ認証基盤を移行する場合
- JWT検証失敗時のエラーレスポンス形式を共通化する場合

## 追記: JWT issuer claim を JwtDecoder 側で検証する（2026-05-21）

### 背景

前段階では、`/login` 成功時に JWT access token を発行し、保護APIでは Spring Security Resource Server + `JwtDecoder` により Bearer token として送られた JWT を検証できる状態にした。

この時点で、JWT には `iss`, `sub`, `iat`, `exp` を含めていたが、`iss` を JWT に入れることと、受け取った JWT の `iss` を検証することは別である。

JWT の payload は暗号化されていないため、`iss` は誰でも読むことができる。したがって、保護API側では、署名や期限だけでなく、JWT の `iss` が OrgFlow の期待する issuer と一致することも検証する必要がある。

### 決定

OrgFlow Phase 1 では、JWT の issuer claim を `JwtDecoder` 側で検証する。

具体的には、`JwtConfig#jwtDecoder()` で `NimbusJwtDecoder` を生成した後、`JwtValidators.createDefaultWithIssuer(jwtProperties.getIssuer())` により issuer 検証を含む validator を作成し、`decoder.setJwtValidator(...)` で `JwtDecoder` に設定する。

これにより、保護APIへ送られた JWT の `iss` が `jwt.issuer` と一致しない場合、Controller 到達前に Spring Security により 401 として拒否される。

### 採用理由

`JwtTokenService` は JWT 発行時に `iss` を claim として入れる責務を持つ。

一方、保護APIに送られた JWT の検証は、Controller / Service ではなく Spring Security Resource Server の処理として Controller 到達前に行う。

そのため、issuer 検証は `SecurityConfig` に直接書くのではなく、JWT を検証する部品である `JwtDecoder` に validator として設定するのが自然である。

また、`SecurityConfig` は URL ごとの認証要否と Resource Server 設定を担当し、`JwtConfig` は JWT 発行・検証に必要な部品を作る責務を持つ。issuer 検証を `JwtConfig` 側に置くことで、この責務分担を維持できる。

### 実装上の整理

`jwtDecoder()` は、JWT をその場で受け取って検証するメソッドではない。

`@Bean` として、Spring Security が後で利用する `JwtDecoder` Bean を作るメソッドである。

そのため、`NimbusJwtDecoder.withSecretKey(...).macAlgorithm(...).build()` により `NimbusJwtDecoder` を生成し、一度変数に受けてから `setJwtValidator(...)` で issuer 検証ルールを登録する。

```java
NimbusJwtDecoder decoder = NimbusJwtDecoder.withSecretKey(createSecretKey())
    .macAlgorithm(MacAlgorithm.HS256)
    .build();

OAuth2TokenValidator<Jwt> jwtValidator =
    JwtValidators.createDefaultWithIssuer(jwtProperties.getIssuer());

decoder.setJwtValidator(jwtValidator);

return decoder;
```

### 確認したこと

Postman で以下を確認した。

- 正常な issuer の JWT を Bearer token として `/hello-auth` に送ると 200
- JWT なしで `/hello-auth` を呼ぶと 401
- 改ざんJWTを送ると 401
- 期限切れJWTを送ると 401
- issuer が想定外の JWT を送ると 401

issuer 不一致の確認では、単純に payload の `iss` を手で書き換える方法は採らなかった。

payload を手で書き換えると署名が壊れるため、issuer検証ではなく署名検証で落ちる可能性が高いからである。

そのため、一時的に `JwtTokenService` の発行処理で `iss = "orgflow-other"` を入れ、同じ secret で署名された JWT を発行した。

その JWT を `/hello-auth` に送ると 401 になったため、署名検証ではなく issuer 検証により拒否できることを確認した。

確認後、一時的な issuer 変更は元に戻し、通常の発行処理では `jwtProperties.getIssuer()` を使う状態に戻した。

### 採用しなかった案

#### 案A: JWT payload の `iss` を手で書き換えて確認する

採用しなかった。

payload を書き換えると署名が一致しなくなるため、issuer 不一致ではなく署名不一致として 401 になる可能性が高い。

今回確認したいのは、「署名は正しいが issuer が想定外の JWT を拒否できるか」であるため、この方法は目的に合わない。

#### 案B: Controller / Service 側で issuer を確認する

採用しなかった。

JWT の検証は Controller 到達前に Spring Security Resource Server 側で行うべきであり、Controller / Service に到達してから issuer を確認すると、認証済みでない token をアプリケーション層で扱うことになる。

OrgFlow Phase 1 では、認証処理と業務処理の責務を分けるため、issuer 検証は `JwtDecoder` 側に置く。

#### 案C: issuer 検証を実装しない

採用しなかった。

JWT に `iss` を含めている以上、保護API側で期待する issuer と一致するかを検証しないと、claim を設計した意味が弱くなる。

また、後続で外部IdPや認可サーバーを検討する際にも、「誰が発行した token か」を検証する考え方は重要になる。

### 受け入れる制約

Phase 1 では、issuer は `orgflow-api` のような単一の固定値として扱う。

複数issuer、外部IdP、JWK Set URI、公開鍵方式、Cognito / Auth0 / Keycloak 連携は現時点では扱わない。

また、`OAuth2TokenValidator<Jwt>` や `NimbusJwtDecoder` の内部実装までは深掘りしすぎず、Spring Security Resource Server の差し込み口として理解する。

### 見直す条件

以下の場合は、issuer 検証の設計を見直す。

- 外部IdPを導入する場合
- HS256 + 自前secret から、公開鍵方式や JWK Set URI 方式へ移行する場合
- 複数issuerの token を受け入れる必要が出た場合
- tenant ごとに issuer を分けるような設計が必要になった場合

## 追記: JWT検証後に `sub` から認証済みuserIdを取り出す方針（2026-05-24）

### 背景

これまでに、`/login` 成功時に JWT access token を発行し、保護APIでは Spring Security Resource Server + `JwtDecoder` により、Bearer token として送られたJWTを検証できる状態にしていた。

また、JWTには以下の claim を含めている。

- `iss`: issuer
- `sub`: userId
- `iat`: 発行時刻
- `exp`: 有効期限

このうち `sub` には、変更される可能性のある `loginId` ではなく、`users.id` を文字列化して入れる方針を採っている。

今回の課題は、JWT検証後に、保護API内で「このリクエストを実行しているuserは誰か」を扱えるようにすることだった。

### 決定

JWT検証後の認証済みuserId取得は、次の方針で扱う。

- Controllerでは `@AuthenticationPrincipal Jwt jwt` により、Spring Securityが保持している検証済みJWTを受け取る
- `Jwt#getSubject()` から `sub` claim を取得する
- `sub` を `UUID` に変換し、OrgFlow上の認証済み `userId` として扱う
- `sub` から `UUID userId` への変換処理は、各Controllerに直接書かず、`JwtUserIdExtractor` に分離する
- Service層には `Jwt` や `Authentication` ではなく、`UUID userId` を渡す

### 採用理由

ControllerはHTTPリクエストの入口であり、Spring Securityから渡される `Jwt` を受け取る位置として自然である。

一方で、Service層は業務処理を担当する層であるため、Spring Security固有の `Jwt` や `Authentication` に依存させない方がよい。

そのため、Controller側で認証済みJWTを受け取り、アプリケーションで扱いやすい `UUID userId` に変換したうえでServiceへ渡す方針とした。

また、`UUID.fromString(jwt.getSubject())` は短い処理ではあるが、複数Controllerに直書きすると以下の問題が起きる。

- 同じ変換処理が複数箇所に散らばる
- `sub` が不正な場合の例外処理がControllerごとにばらつく
- 「JWTのsubから認証済みuserIdを取り出す」という意味がController内に埋もれる
- 後で取得方法を変える場合に修正箇所が増える

そのため、`JwtUserIdExtractor` という小さな部品に切り出すことにした。

### 実装上の整理

今回、以下を追加した。

- `com.yoshida.orgflow.security.JwtUserIdExtractor`
  - `Jwt` を受け取り、`jwt.getSubject()` を `UUID` に変換する
  - `@Component` を付け、Spring管理の部品として扱う
  - Controllerからコンストラクタインジェクションで利用する

- `com.yoshida.orgflow.common.exception.InvalidJwtSubjectException`
  - JWTの `sub` がOrgFlowの `userId` として扱えない場合を表す例外
  - `IllegalArgumentException` をそのまま外へ漏らさず、認証情報のclaim不正として意味づけする

- `GlobalExceptionHandler`
  - `InvalidJwtSubjectException` をHTTP 401に変換する
  - 外部向けメッセージは `"認証情報が不正です"` に丸める

### 確認したこと

Postmanにより、以下を確認した。

- 正常JWTで `/hello-auth` を呼ぶと 200
- `@AuthenticationPrincipal Jwt jwt` により、Controllerで検証済みJWTを受け取れる
- `Jwt#getSubject()` から `sub` を取得できる
- `sub` を `UUID` に変換できる
- 一時的に `JwtTokenService` の `.subject(userId.toString())` を不正値へ変更し、`sub` がUUID形式でないJWTを発行すると `/hello-auth` が401になる
- `JwtTokenService` の一時変更を元に戻した後、正常JWTで `/hello-auth` が200になる
- `mvn test` が成功する

### 採用しなかった案

#### 案A: Controllerごとに `UUID.fromString(jwt.getSubject())` を直接書く

採用しなかった。

処理自体は短いが、今後保護APIが増えると、認証済みuserId取得処理が複数Controllerに散らばる。

また、`sub` が不正な場合の扱いもControllerごとにばらつきやすくなるため、`JwtUserIdExtractor` に分離した。

#### 案B: `Authentication#getName()` からuserIdを取得する

採用しなかった。

今回の確認では、`Authentication#getName()` と `Jwt#getSubject()` が同じUUID文字列を返すことを確認した。

ただし、`getName()` はコードだけ見ると「JWTのsubjectを取得している」ことが読み取りにくい。

今回の学習・設計意図は、JWTの `sub` から `users.id` を取り出すことであるため、`Jwt#getSubject()` を使う方が説明しやすい。

#### 案C: Service層へ `Jwt` をそのまま渡す

採用しなかった。

Service層は業務処理を担当する層であり、Spring SecurityやJWTの具体型を直接知る必要はない。

Service層では、認証済みuserを表す情報として `UUID userId` を受け取ればよい。

#### 案D: `IllegalArgumentException` をそのまま外へ投げる

採用しなかった。

`IllegalArgumentException` は、UUID変換失敗以外にもさまざまな箇所で発生しうる。

そのため、`IllegalArgumentException` のままでは、「認証情報のclaim不正」なのか「業務入力値の不正」なのか区別できない。

今回は、JWTの `sub` がOrgFlowの認証済みuserIdとして扱えないことを明示するため、`InvalidJwtSubjectException` に変換する方針とした。

### この判断で得られるもの

- 保護API内で、認証済みuserIdを `UUID` として扱える
- ControllerからServiceへ、Spring Security固有型ではなくアプリケーション上の識別子を渡せる
- tenant選択、RBAC、監査ログ記録へ進む前提ができる
- JWTの `sub` が不正な場合に、500ではなく401として扱える
- 認証情報の不正と業務入力値の不正を例外型で区別できる

### この判断で受け入れる制約

- 現時点では、`sub` から取得した `userId` がDB上に実在するかまでは確認していない
- 現時点では、tenant membership や role の確認は行っていない
- 現時点では、`/hello-auth` は認証済みuserId取得の確認用APIであり、本来の業務APIではない
- JWT検証そのものに失敗した場合の401と、JWT検証後に `sub` がOrgFlowの前提を満たさなかった場合の401は、処理経路が異なる

### 見直す条件

以下の場合は、この判断を見直す。

- `sub` 以外のclaimも使って認証済みユーザー情報を組み立てる必要が出た場合
- tenant情報をJWTに含める方針へ進む場合
- `JwtAuthenticationConverter` などを使って、Spring Security側でprincipalやauthorityの変換を行う方針に変更する場合
- Service層へ渡す認証済み利用者情報が `UUID userId` だけでは不足し、独自の認証済みユーザーコンテキストが必要になった場合

## 追記: tenant選択後に current_tenant_id 入りJWTを再発行する方針（2026-06-04）

### 背景

OrgFlow では、`/login` 成功時点で認証済みuserIdは確定する。

ただし、OrgFlow はマルチテナント構成であり、認証済みuserIdだけでは、後続の業務APIをどの tenant 上で実行するかを判断できない。

そのため、ログイン後に user が所属tenantを選択し、その選択結果を後続APIの認可判定で使える形にする必要があった。

### 決定

`/login` 成功時に発行するJWTには、`current_tenant_id` claim を含めない。

`POST /tenants/{tenantId}/select` で、認証済みuserIdと指定tenantIdの membership を確認する。

membership が存在する場合は、`current_tenant_id` claim を含むJWTを再発行して返す。

後続のtenantスコープAPIでは、JWTの `sub` から取得した userId と、`current_tenant_id` を認可判定の前提として扱う。

### 採用理由

`/login` 時点では、user がどのtenantで操作するかはまだ確定していない。

そのため、ログイン直後JWTに `current_tenant_id: null` を入れるのではなく、claim自体を含めない方が、tenant未選択状態を明確に表現できる。

また、tenant選択後にJWTを再発行することで、後続APIは毎回request bodyやquery parameterからtenantIdを受け取らなくても、Bearer token内の `current_tenant_id` を参照してtenant境界を判定できる。

### 不採用案

#### 案A: `/login` 時点で `current_tenant_id: null` をJWTに入れる

`current_tenant_id` claim が存在するのに値がnullという状態になり、claimが必須なのか任意なのかが分かりにくくなるため採用しない。

tenant未選択状態は、`current_tenant_id` claim が存在しないことで表す。

#### 案B: `/login` 時点でデフォルトtenantを自動選択する

user が複数tenantに所属している場合に、どのtenantを自動選択すべきかという追加ルールが必要になる。

また、ユーザー自身が操作対象tenantを選択するという画面導線と合わないため、Phase 1 では採用しない。

#### 案C: tenantIdを毎回request bodyやquery parameterで渡す

各APIでtenantIdの受け渡しが重複し、tenant境界の扱いが散らばりやすい。

Phase 1 では、tenant選択後JWTに `current_tenant_id` を含めることで、後続APIの認可判定の前提を揃える。

### エラー方針

`POST /tenants/{tenantId}/select` では、JWTなし・JWT不正・期限切れ・issuer不一致など、Spring Securityで認証できない場合は401とする。

JWTは有効だが、指定tenantIdに対応するmembershipが存在しない場合は404とする。

このとき、tenant自体が存在しない場合と、tenantは存在するがuserが所属していない場合を外部レスポンスでは区別しない。

外部向けメッセージは `"対象のtenantが見つかりません"` に丸める。

### 受け入れる制約

`current_tenant_id` がないJWTでも呼べるAPIと、`current_tenant_id` が必要なAPIを分けて扱う必要がある。

Phase 1では、`POST /tenants/{tenantId}/select` と、将来追加予定の `GET /me/tenants` は `current_tenant_id` なしJWTでも呼べるAPIとする。

一方、申請作成、承認、差し戻し、監査ログ閲覧などのtenantスコープ業務APIは、`current_tenant_id` 入りJWTを前提とする。

### 見直す条件

外部IdPやOIDC連携を導入する場合。

Refresh token / access token の構成を導入する場合。

tenant選択状態をサーバー側セッションやDBに保持する設計へ変更する場合。

tenant role や権限情報をJWT claimへ含める必要が出た場合。

## 追記: tenantスコープAPIでの current_tenant_id 取得方針（2026-06-11）

### 決定

tenantスコープAPIでは、JWT内の `sub` と `current_tenant_id` をそれぞれ次のように扱う。

- `sub`
  - 認証済みuserを示すclaim
  - `JwtUserIdExtractor` で `UUID userId` に変換する
- `current_tenant_id`
  - 現在選択中tenantを示すclaim
  - `JwtCurrentTenantIdExtractor` で `UUID currentTenantId` に変換する

`current_tenant_id` がJWTに存在しない場合は、tenant未選択状態として扱う。

この場合、JWT自体は有効であり、利用者の認証は成立している。
しかし、tenantスコープAPIを実行するための前提を満たしていないため、外部レスポンスは `403 Forbidden` とする。

一方、`current_tenant_id` が存在するがUUIDとして解釈できない場合は、JWT内の認証情報が不正な状態として扱う。
この場合は、外部レスポンスを `401 Unauthorized` とし、外部向けメッセージは `"認証情報が不正です"` に丸める。

### 採用理由

`userId` と `currentTenantId` は、どちらも後続APIで重要な認証・認可の前提になるが、意味が異なる。

`userId` は「誰がログインしているか」を示す。
一方、`currentTenantId` は「現在どのtenantで操作するか」を示す。

この2つを同じExtractorにまとめると、認証済み主体の取得とtenant選択状態の取得が混ざる。
そのため、Phase 1では次のように処理部品を分ける。

- `JwtUserIdExtractor`
  - `sub` から `userId` を取得する
- `JwtCurrentTenantIdExtractor`
  - `current_tenant_id` から `currentTenantId` を取得する

また、`current_tenant_id` 欠落とUUID形式不正は、外部レスポンス上も意味が異なる。

- 欠落
  - ログイン済みだがtenant未選択
  - 403
- UUID形式不正
  - JWT内のclaimが不正
  - 401

この違いを例外クラスでも分けることで、`GlobalExceptionHandler` でHTTPステータスと外部向けメッセージを明確に対応づけられる。

### 実装上の対応

今回、次のクラスを追加した。

- `CurrentTenantNotSelectedException`
- `InvalidJwtCurrentTenantIdException`
- `JwtCurrentTenantIdExtractor`

また、`GlobalExceptionHandler` に次の変換を追加した。

- `CurrentTenantNotSelectedException`
  - `403 Forbidden`
  - `"tenantが未選択です"`
- `InvalidJwtCurrentTenantIdException`
  - `401 Unauthorized`
  - `"認証情報が不正です"`

疎通確認用に `GET /hello-tenant` を追加し、以下の動作を確認した。

- JWTなし
  - 401
- `/login` 直後JWT
  - 403
  - `current_tenant_id` がないためtenant未選択
- tenant選択後JWT
  - 200
  - `userId` と `currentTenantId` をレスポンスで確認

### 不採用案

#### 案A: `JwtUserIdExtractor` に `current_tenant_id` 取得処理も追加する

不採用理由:

`sub` から `userId` を取り出す処理と、`current_tenant_id` から `currentTenantId` を取り出す処理では、意味と失敗時の扱いが異なる。

`sub` の不正は認証済み主体の不正であり、`current_tenant_id` の欠落はtenant未選択状態である。
同じクラスにまとめると、責務が広がり、例外設計も分かりにくくなる。

#### 案B: `current_tenant_id` がない場合を401にする

不採用理由:

JWT自体は有効であり、利用者の認証は成立している。
問題は、tenantスコープAPIに必要なtenant選択状態を満たしていないことなので、認証失敗を示す401ではなく403にする。

#### 案C: `current_tenant_id` がない場合を404にする

不採用理由:

404は、指定されたリソースやtenantの存在を外部に見せないために使う場面では有効である。
しかし、今回のエラーは特定tenantの存在有無ではなく、JWTに選択中tenantが含まれていない状態である。
そのため、404ではなく403にする。

#### 案D: `current_tenant_id` がUUIDとして不正な場合を400にする

不採用理由:

400は、リクエストbodyやpath parameterなど、クライアント入力の形式不正に寄せる方が自然である。
今回壊れているのは、認証情報として使っているJWT内のclaimである。
そのため、`sub` 不正時と同様に、認証情報不正として401に寄せる。

### 受け入れる制約

tenantスコープAPIを実装するたびに、`userId` と `currentTenantId` の取得をどうController / Serviceへ渡すかを考える必要がある。

現時点では、Controllerで `@AuthenticationPrincipal Jwt` を受け取り、Extractorで `UUID userId` と `UUID currentTenantId` に変換してServiceへ渡す方針とする。

ただし、後続APIが増えてControllerごとに同じ処理が繰り返される場合は、認証済み利用者とcurrent tenantをまとめた専用オブジェクト、または引数解決の仕組みを検討する余地がある。

### 見直す条件

- tenantスコープAPIが増え、Controllerで毎回 `JwtUserIdExtractor` と `JwtCurrentTenantIdExtractor` を呼ぶ重複が目立つ場合
- `userId` と `currentTenantId` に加えて、tenant role や internal organization role も共通で扱う必要が出た場合
- 外部IdP / OIDC / Refresh token 構成を導入する場合
- tenant選択状態をJWTではなくサーバー側セッションやDBに保持する設計へ変更する場合

## 追記: `GET /me/tenants` は current_tenant_id を不要とする（2026-06-19）

### 背景

`POST /tenants/{tenantId}/select` により、tenant選択後JWTには `current_tenant_id` を含める方針にした。

一方で、ログイン直後のJWTには `current_tenant_id` が含まれていない。
この状態でも、利用者は自分が所属しているtenant一覧を取得し、どのtenantを選択するか決める必要がある。

そのため、tenant選択前でも呼べる所属tenant一覧取得APIの扱いを決める必要があった。

### 決定

`GET /me/tenants` は、認証済みuserが所属しているtenant一覧を取得するAPIとして扱う。

このAPIでは、JWT内の `sub` から取得した `userId` のみを使用し、`current_tenant_id` は使用しない。

そのため、次のどちらのJWTでも呼び出せる。

- `/login` 直後の `current_tenant_id` なしJWT
- tenant選択後の `current_tenant_id` ありJWT

所属tenantが0件の場合は、例外ではなく `200 OK` と空配列を返す。

### 採用理由

`GET /me/tenants` は、tenantスコープAPIではなく、tenantを選択する前段の導線APIである。

ログイン直後のJWTには `current_tenant_id` が含まれていない。
この状態で所属tenant一覧を取得できないと、利用者はどのtenantを選択できるか分からない。

また、tenant選択後であっても、別tenantへ切り替えるために所属tenant一覧を再取得する可能性がある。
そのため、このAPIは `current_tenant_id` の有無に依存させない。

### 採用しなかった案

#### 案A: `current_tenant_id` がない場合は403にする

`GET /me/tenants` はtenantスコープAPIではないため、tenant未選択状態をエラーにするとログイン後のtenant選択導線が成立しない。

#### 案B: クライアントからuserIdを受け取る

認証済みuser自身のtenant一覧を返すAPIであり、クライアントにuserIdを指定させる必要はない。
JWTの `sub` を使うことで、「誰のtenant一覧か」をサーバー側で決定できる。

### この判断で得られるもの

- ログイン後に所属tenant一覧を取得できる
- tenant選択前とtenant選択後のどちらでもtenant切替導線を維持できる
- tenantスコープAPIと、tenant選択前導線APIの責務を分けて説明できる

### この判断で受け入れる制約

`GET /me/tenants` では、tenant内の権限やinternal organization単位の権限は扱わない。
返す情報は、Phase 1では `tenantId` と `tenantName` の最小情報に絞る。

### 見直す条件

tenant一覧画面で、tenant role、最終選択日時、表示順、利用停止状態などを返す必要が出た場合。

また、tenant選択状態をJWTではなくサーバー側セッションやDBで管理する設計へ変更する場合。
