# ADR-037: 状態の移り変わりは request 自身の操作メソッドでだけ起こす

- Status: Accepted
- Date: 2026-10-11
- 関連: ADR-004（状態と遷移の表） / ADR-031（不正な遷移は 409） / ADR-035（状態列は text と CHECK 制約） / ADR-039（submit の判定順序）

> **決定**: request の状態を変えるのは、request 自身が持つ操作のメソッド（submit・approve・return・reject・cancel）だけにする。各メソッドは、今の状態から ADR-004 の表で許される遷移かを確かめてから状態を変え、許されなければ例外を投げる（409）。状態を任意の値に書き換える setter は持たない。

## 背景

submit を実装するにあたり、ADR-004 で決めた遷移の表（`draft` から行けるのは `in_progress` と `cancelled` だけ、など）を、コードのどこで守るかを決める必要があった。

Phase 1 では submit に続いて approve・return・reject・cancel も実装するため、状態を変える操作は 5 つになる。どの操作も「今の状態ならこの操作ができる」を確かめる必要がある。

request のエンティティは、作成時に状態を `draft` に決めるだけで、作成後に状態を変える手段を持っていなかった。

## 理由

- 状態を変える入口が、確かめの付いたメソッドだけになる。setter があると、確かめを書き忘れた処理からも状態を書き換えられてしまう
- 遷移の規則が request の中にまとまり、操作が増えても置き場所が散らばらない
- 規則のテストを、mock を使わずにエンティティ単体で書ける（作成時の固定値のテストと同じ形）
- 作成時の状態を request 自身が決めている（`draft`）のと、考え方がそろう
- Service は「申請を読む → 権限を確かめる → 操作を呼ぶ → 保存する」という手順に専念できる

## 検討した他の案

- **案A: Service に if で書き、エンティティに状態の setter を足す** — よく見る形で変更量も少ないが、setter が抜け道になり、確かめを書き忘れた処理から不正な遷移ができてしまう。規則が Service の各メソッドに散らばる
- **案B: 状態を enum にし、遷移の表をそのまま enum に写して各操作から参照する** — 表が 1 か所にまとまる利点はあるが、状態の型を文字列から enum に変える変更が要る。この決定の中身を後から置き換えられるため、今は採らない

## 受け入れる制約

- 操作ごとに、許される元の状態をメソッドの中に書くため、ADR-004 の表と各メソッドの記述が二重になる。表を変えたときは、該当するメソッドをすべて直す必要がある
- エンティティが業務の規則を持つため、エンティティを「DB の行を写すだけの入れ物」として扱う書き方とは異なる

## 見直す条件

- 操作が増え、各メソッドに書いた規則と ADR-004 の表が食い違い始めた場合（案B の enum に寄せる）
- 状態を変える操作が、request 以外のデータ（承認ルートの適用結果など）の状態にも強く依存するようになった場合
